# Art Tech Spec

The technical spec that makes the look reproducible in code: the isometric grid and screen math, sprite anchoring, depth sorting, and the code-generated pixel art format. What things look like (palettes, factions, VFX, tells, UI) is in [art-direction.md](art-direction.md). The renderer that consumes this spec is in [architecture.md § Rendering](../tech/architecture.md#rendering).

Binding constraint: **D001 #1.** All art is generated by code from palette-indexed grids.

---

## 1. Isometric spec

### Tile and screen

| Item | Value |
|---|---|
| Tile footprint | **32 × 16 px diamond** (2:1 dimetric, the classic "pixel isometric") |
| Elevation step | 8 px per level (cliff side faces drawn below the diamond) |
| Internal render resolution | **640 × 360** (16:9) |
| Scaling | **Integer only**: 2× = 1280×720, 3× = 1920×1080, 4× = 2560×1440, 6× = 3840×2160. Letterbox with `ink.0`. |
| Map size without panning | `cols + rows ≤ 36`. Every campaign map fits on one screen ([design/maps.md §1](../design/maps.md#1-grid-and-coordinates)). Only endless and challenge maps may be larger and pan. |

**Screen budget for the largest campaign map** (22×14, Act III and the finale): the diamond is `(cols + rows) × 16` by `(cols + rows) × 8` = **576 × 288 px**. Add up to 32 px of tower overhang above the top row and 8 px for high ground, and it fits in **576 × 328** of the 640 × 360 view, leaving 32 px side margins. An isometric diamond leaves the four screen corners empty, so the HUD lives in the corners ([art-direction.md §9](art-direction.md#9-ui-style)) and never covers tiles. The camera centers the map's bounding box and doesn't move on campaign maps.

**Why 640×360 and 32×16:** 640×360 scales to every common 16:9 display by an integer, so there are no mixels anywhere. A 32×16 tile gives towers about 32×40 px of canvas, which is enough room for readable silhouettes and upgrade tiers while still letting about 18×18 tiles fit on screen.

The scaling factor is computed in **device pixels** so that fractional `devicePixelRatio` values (1.25, 1.5) still map each game pixel to a whole number of physical pixels: `n = max(1, floor(min(innerWidth·dpr / 640, innerHeight·dpr / 360)))`, with the canvas CSS size set to `640·n / dpr` by `360·n / dpr`. The implementation is in `src/render/scale.ts` ([architecture.md § Rendering](../tech/architecture.md#rendering)).

### The canonical tile mask

Ground tiles tile seamlessly at a step of (16, 8) with no overlap and no gaps when the diamond is exactly this shape (256 px, which equals the lattice cell area):

```
row r (0..7):   x from 15−2r to 16+2r   (widths 2, 6, 10, … 30)
row r (8..15):  mirror of row 15−r
```

The two widest rows (7 and 8) are 30 px wide. The tile's extreme left and right points (x = 0 and x = 31) are owned by neighboring tiles. The procedural tile generator and the buildable-tile overlay both use this mask.

### Grid ↔ screen math

The grid is a continuous coordinate space in **tile units**, addressed as `(col, row)` in design docs and map data. In code, `gx = col` and `gy = row`. Tile `(i, j)` covers `[i, i+1) × [j, j+1)`, and its center is `(i + 0.5, j + 0.5)`. The sim works only in grid units; the render layer converts.

```ts
const TW = 32, TH = 16;          // tile width/height in px
const HW = TW / 2, HH = TH / 2;  // 16, 8
const ZH = 8;                    // px per elevation level

// grid → screen (world pixels, before camera scroll)
sx = (gx - gy) * HW + originX
sy = (gx + gy) * HH + originY - z * ZH

// screen → grid (z = 0)
const u = (sx - originX) / HW, v = (sy - originY) / HH;
gx = (u + v) / 2
gy = (v - u) / 2
// picking a tile: (floor(gx), floor(gy)), then bounds-check
```

`originX/originY` is the screen position of grid point `(0, 0)`, the top vertex of tile `(0, 0)`. A tile image (32×16) is drawn with its top-left at `(sx(i, j) − 16, sy(i, j))`. **All final screen positions are rounded to integers** (`Math.round`) before they reach Phaser.

The implementation is `src/render/iso.ts` (tested in `iso.test.ts`). Two details it settles:
- **Picking snaps to the game pixel.** The pointer position is first moved to the center of the game pixel it falls in, then projected and floored. Pixel centers never lie on a diamond edge, so picking matches [the canonical tile mask](#the-canonical-tile-mask) exactly: each mask pixel picks its own tile and no pixel picks two. High ground is tested first at elevation 1 (its top face, drawn `ZH` higher, covers the tiles behind it); a point on its cliff faces falls in its own ground footprint, so it picks the raised tile too.
- **Centering** (`mapOrigin`): the origin centers the ground diamond horizontally, and centers the diamond plus 40 px of headroom above it (tower overhang and one elevation step) vertically, in whole pixels. A1M1 (14 × 10) gets origin (288, 104) in the 640 × 360 view.

**Ranges are circles in grid space**, so they appear on screen as 2:1 ellipses. Range rings are pre-rasterized pixel ellipses ([art-direction.md §7](art-direction.md#range-rings-and-placement)), not anti-aliased vector shapes.

### Sprite anchoring

Every sprite definition declares an **anchor**: the point that sits on the ground point (the foot point). It is a whole-pixel **edge** coordinate, exactly what the renderer passes to `setDisplayOrigin(ax, ay)` (never a fraction): `(16, 0)` on a 32 px tile is the top vertex between pixels 15 and 16. The outline pass shifts it by 1, a mirrored frame's anchor is `w − ax`, and `SpriteSource.frameAnchor` returns each baked frame's own anchor.

| Thing | Ground point | Typical canvas | Anchor convention |
|---|---|---|---|
| Ground tile | top vertex of tile | 32×16 (+8 per elevation level) | top-left at `(sx − 16, sy)` |
| Tower | tile center | up to 32×48 | the center of the base's footprint diamond (where it meets the ground), horizontally centered |
| Enemy (small / medium / large) | its grid position | 10–16 / 16–24 / 24–32 px | between the feet, 1 px above the bottom row |
| Boss | its grid position | up to 64×64 | between the feet |
| Flying enemy | ground position (shadow) | as above | sprite drawn 12 px above the anchor, with a shadow blob at the anchor |
| Contact shadow (ground enemy) | the enemy's grid position | 18×6 (`fx.ground_shadow`: `small`, `medium`, `large`) | center; drawn in `decal` at 35% (`groundShadowFor(spriteId)` in `src/content/sprites/shadows.ts` picks the frame by the body's width and gives the alpha). Towers and props bake their own shadow into the frame |
| Allied unit (for example Skitterkin swarmlings sent out by a tower) | its grid position | 8–12 px | between the feet |
| Projectile | its grid position | 2–8 px | center |
| Prop (single tile) | tile center | up to 32×48 | as towers |

### Depth sorting

The world is drawn in **fixed layers** (Phaser `Layer`s), bottom to top:

| # | Layer | Contents | Sorting |
|---|---|---|---|
| 1 | `backdrop` | Sky gradient, stars, far parallax | none |
| 2 | `ground` | Ground tiles, cliffs, water | static, by `(i + j)` then `i` |
| 3 | `decal` | Path markings, buildable-tile markers, range rings, shadows, scorch marks | insertion order |
| 4 | `world` | Towers, ground enemies, props, tall terrain | **`depth = footY + kindBias + (uid & 0xff) / 1e4`** |
| 5 | `air` | Flying enemies, lobbed projectiles at the top of their arc | same formula |
| 6 | `vfx` | Projectiles, impacts, particles, glow sprites (additive) | insertion order |
| 7 | `lighting` | Darkness overlay (A2M6 through the finale) with light punch-outs | none |
| 8 | `overlay` | Health bars, tells, floating credits, selection brackets | insertion order |

- `footY` is the anchor's screen y **on the ground plane** (no elevation offset). `kindBias`: prop 0.1, enemy 0.2, tower 0.3, so at equal y, towers draw in front.
- The `uid` term breaks ties deterministically so sprites never flicker.
- **Multi-tile props** sort by their front-most (largest `footY`) tile. If a large prop clips wrong, split it into per-tile slices.
- **Elevation:** the playfield has at most **one raised level**: **high ground** tiles (buildable, +range; [design/maps.md](../design/maps.md)). A high-ground tile is a block (diamond top plus 8 px cliff faces) drawn in the **`world` layer** with `kindBias` 0.05, so things in front of it draw over its cliff faces and things behind it are hidden. A tower on high ground draws its anchor `ZH` (8 px) higher but sorts by the tile's ground-plane `footY`. Decorative cliffs at the map edges stay in the `ground` layer. Playfields with more than one raised level are out of scope.

## 2. Code-generated pixel art format

Per D001, sprites are **palette-indexed character grids** in TypeScript data files. At boot they're rasterized into RGBA buffers, packed into a texture atlas, and registered with Phaser. Nothing about the format is Phaser-specific.

### Files

| Path | Contents |
|---|---|
| `src/content/palettes/master.ts` | The master palette ([art-direction.md §2](art-direction.md#2-master-palette)), as `name → hex`, including the namespaced environment ramps (`act1.grass.2`). **The home of every hex value.** |
| `src/content/palettes/factions.ts`, `env.ts`, `index.ts` | Faction slot palettes ([art-direction.md §4](art-direction.md#4-faction-visual-language)), environment slot palettes and sky gradients ([art-direction.md §3](art-direction.md#3-environment-palettes-by-act)), and the `PALETTES` registry |
| `src/content/palettes/color.ts` | Luminance, contrast ratio, and the Hollow hue-reservation test |
| `src/content/sprites/types.ts`, `legend.ts`, `defineSprite.ts` | The data shapes (`SpriteDef`, `Slot`, `SlotPalette`, `PaletteId`, `EnvPaletteId`), the standard legend, and the identity helper |
| `src/content/sprites/helpers.ts` | Procedural helpers: the tile mask, `diamond`, `isoBox`, `disc`, `line`, `stamp`, `mirrorRows`, `recolor`, seeded `hash01` |
| `src/content/sprites/validate.ts` | `validateSprites()`: ids, grids, patches, mirrors, anims, legend colors, palette references (errors name sprite, frame, row, column) |
| `src/content/sprites/<category>/<id>.ts` | One sprite per file (a tower's file holds its base and head). Categories: `tiles`, `props`, `towers`, `enemies`, `projectiles`, `fx`, `icons`, and later `portraits`, `ui`. Shared builders sit beside them (`tiles/tileGen.ts`, `towers/base.ts`, `enemies/skitter.ts`, `icons/iconGen.ts`, `icons/enemyIcon.ts`); the HUD's 8×8 glyphs and tell glyphs share `icons/glyphs.ts`. `tiles/apron.ts` holds the apron tiles ([art-direction.md § The apron](art-direction.md#the-apron-every-act)) and `shadows.ts` the contact-shadow lookup |
| `src/content/sprites/index.ts` | `SPRITES`, the registry of all sprites in gallery order, and the `SpriteId` union |
| `src/render/sprites/rasterize.ts` | **Pure** pixel passes on char-code grids: parse, patch, mirror, outline, colorize, glow. No DOM, no Phaser, so it's unit-tested in Node. |
| `src/render/sprites/bake.ts` | **Pure** baker: definition × palettes → keyed RGBA frames, anims, and meta |
| `src/render/sprites/atlas.ts` | **Pure** shelf packer (max 2048×2048 pages, 1 px gutter, pages trimmed to their used size) |
| `src/render/sprites/canvas.ts`, `CodeSpriteSource.ts` | Buffers → canvases; registers atlas pages (`sprites.0`, …), frames, and animations with Phaser |
| `gallery.html`, `src/app/gallery.ts` | The sprite gallery dev page (below) |

### The standard legend

Every sprite uses this legend unless it adds its own entries. Each character names a **slot**, and a palette maps slots to master colors, so one grid can be re-skinned by swapping the palette.

| Char | Slot | Meaning |
|---|---|---|
| `.` | — | transparent |
| `0`–`4` | `p0`–`p4` | primary ramp (0 darkest) |
| `5`–`9` | `s0`–`s4` | secondary ramp |
| `a`–`e` | `a0`–`a4` | accent ramp |
| `+` | `e0` | emissive glow (outer) |
| `*` | `e1` | emissive core |
| `x` | `outline` | hand-placed outline pixel |
| `k` | `eye` | pupils, the darkest detail |
| `w` | `hi` | specular glint |
| `_` | `shadow` | ground shadow (`ink.0` at 50% alpha) |
| `A`–`Z` | custom | per-sprite legend entries mapping directly to master colors (use sparingly) |

### Example: a small Skitterkin enemy

Illustrative only; the real roster is in [design/enemies.md](../design/enemies.md).

```ts
// src/content/sprites/enemies/example_mite.ts
import { defineSprite } from '../defineSprite';

export const exampleMite = defineSprite({
  id: 'enemy.example_mite',
  size: { w: 12, h: 10 },
  anchor: { x: 6, y: 9 },        // between the feet
  palette: 'skitterkin',         // default palette (slot → master color)
  variants: ['skitterkin.ally'], // extra palette variants to bake
  outline: 'auto',               // baker adds a 1px `outline` ring; size and anchor grow by 1
  glow: { slots: ['e0', 'e1'], radius: 2 }, // bakes an additive halo frame
  frames: {
    walk_se_0: [
      '.....aa.....',
      '....1221....',
      '..11233221..',
      '.1123344321.',
      '.12kw23kw21.',
      '112kk233kk21',
      '.1127887211.',
      '..11*77*11..',
      '...111111...',
      '..0.0..0.0..',
    ],
    // A patch frame: copy walk_se_0 and overwrite only the rows that change.
    walk_se_1: { from: 'walk_se_0', patch: { x: 0, y: 9, rows: ['.0.0....0.0.'] } },
  },
  anims: {
    walk_se: { frames: ['walk_se_0', 'walk_se_1'], fps: 8 },
    walk_sw: { mirrorOf: 'walk_se' },  // horizontal mirror, no extra authoring
    // walk_ne / walk_nw: back views, authored separately (no eyes), then mirrored
  },
});
```

### Format rules

- **Grids are validated:** every row must have exactly `w` characters, there must be `h` rows, and every character must be in the legend. Errors name the sprite, frame, row, and column.
- **Frames** are a grid, a patch (`{ from, patch }`, one patch or a list), or a mirror (`{ mirrorOf }`). In patch rows `.` writes transparency and a **space keeps** the pixel underneath. Patches must fit inside the frame.
- **Mirror anims** (`{ mirrorOf: 'walk_se' }`) name each mirrored frame by swapping the facing token in the source frame's name, as a whole `_`-separated token (`se`↔`sw`, `ne`↔`nw`): `walk_se_0` → `walk_sw_0`, `se_fire` → `sw_fire`. A mirrored name that is also authored is an error.
- **Facings:** actors that move have 4 diagonal facings (SE, SW, NE, NW). Author SE and NE; SW and NW are `mirrorOf`. Tower heads that aim may author up to 8 facings (4 authored + mirrors); the minimum is SE and NE.
- **No runtime rotation of pixel art.** Rotating a sprite blurs or jags it unpredictably. Exceptions: projectiles of 4 px or smaller, and particles.
- **Composition:** a tower is a `base` sprite plus a `head` sprite (`tower.<id>` and `tower.<id>_head`). The head's anchor is drawn at the base's `mount: { x, y }` (authored pixels; `SpriteSource.mount` returns it in outlined pixels). Tier visuals are separate frames or patches of the same sprite (`t1`, `t2`, `t3`, `spec_a`, `spec_b`). Everglow bases share one builder: the teal logo chevron on the left face and one orange chevron per tier on the right face. Tiers also change the silhouette so they read at 1× without the chevrons: T2 bolts a striped armor pod onto each side corner (4+ px wider), and T3 adds a sensor mast with a teal tip on the left pod (6+ px taller). The head is the same at every tier. Heads that aim author `se`, `ne`, `se_fire`, `ne_fire` and get `sw`/`nw` from `fire_sw`/`fire_nw` mirror anims; heads that don't aim (Sprinkler) author an idle cycle.
- **Tiles** are 32×16 with anchor `(16, 0)` and no outline. They use environment palettes, whose slots are mapped the same way in every act: `p` ground (grass; Act III and finale ground), `s` path, `a` clay/cliff (Act III and finale: crystal), `e0`/`e1` the act's flora accent, `outline` the act's `shade`, `hi` its `light`. Act III's 4-step path ramp repeats its top step, and the finale borrows Act III's path and crystal ramps. Everglow hardware set into tiles (the pad's plate and brackets) uses custom legend entries, so it keeps its steel and teal in every act. Ground tiles ship noise variants (`v0`, `v1`, …); `tile.path` adds `tread_x` and `tread_y` (tread marks along each grid axis).
- **Procedural helpers are allowed.** Sprite files are TypeScript, so a definition can be computed (`mirrorH`, `stamp`, `recolor`, and noise fills for tiles). Ground tiles are mostly generated from the tile mask, the environment ramps, and a seeded noise pattern, not hand-gridded one by one.
- **Animation budget:** idle 2 frames at 2–4 fps, walk 2–4 frames at 6–10 fps, fire 2–3 frames, death 3–5 frames. Walk playback rate scales with the enemy's current speed, so a slowed enemy visibly walks slower.

### What the baker produces

For every sprite × palette variant × frame:

1. **Resolve** patches and mirrors into full grids.
2. **Rasterize** into an RGBA buffer through the palette (pure function, tested).
3. **Outline pass** (`outline: 'auto'`): every transparent pixel that is 4-adjacent to an opaque one becomes the palette's `outline` color. (`'auto8'` uses 8-adjacency for chunkier outlines.) Shadow (`_`) pixels don't grow an outline. Shadow pixels bake at 50% alpha.
4. **Derived variants**, baked automatically for every actor:
   - `selected`: outline replaced with `white.1` (hover and selection). Baked for towers and enemies.
   - `jammed`: every color mapped onto the `steel` step nearest it in luminance (towers under a jam, D001 #4 and [design/enemies.md §4](../design/enemies.md#4-tower-disabling-jamming)). Baked for towers only.
   - Derived variants are named `<variant>+selected` and `<variant>+jammed` and are baked for every palette variant (`default+selected`, `everglow.worn+jammed`).
   - `@glow`: if `glow` is set, emissive pixels (the slots in `glow.slots`) dilated by `radius` with stepped alpha by rounded Euclidean distance (60% on the pixel, 35% at 1 px, 15% at 2 px and beyond; never smooth gradients), each halo pixel taking its nearest emissive pixel's color, drawn additively. The glow frame is padded by `radius` on every side and has its own anchor. Glow frames exist for palette variants, not derived ones.
   - `heavy` (Hollow sprites only): the Heavy tell from [art-direction.md §8](art-direction.md#trait-tells), baked as a variant so render only switches frames.
   - `dark` (portraits only): every color mapped onto `ink.1`–`ink.3` by luminance, outline `ink.0` ([art-direction.md § Portrait roster](art-direction.md#portrait-roster)).
5. **Pack** into atlas pages and register with Phaser.

**Hit flashes are not baked.** They use Phaser 4's tint fill mode at runtime (`setTint(0xffffff)` plus `setTintMode(Phaser.TintModes.FILL)` for 2 frames), which works the same for hand-made sheets.

### Naming contract (what makes the renderer swappable)

Render code never touches grids. It asks a `SpriteSource` for frames by **stable names**:

```
frame key:  <spriteId>#<variant>:<frame>     e.g. enemy.example_mite#default:walk_se_0
anim key:   <spriteId>#<variant>:<anim>      e.g. enemy.example_mite#skitterkin.ally:walk_se
glow frame: <spriteId>#<variant>:<frame>@glow
```

```ts
interface SpriteSource {
  load(scene: Phaser.Scene): Promise<void>;     // registers textures, frames, anims
  frame(spriteId: SpriteId, frame: string, variant?: string): { texture: string; frame: string };
  glowFrame(spriteId: SpriteId, frame: string, variant?: string): { texture: string; frame: string } | null;
  anim(spriteId: SpriteId, anim: string, variant?: string): string;
  meta(spriteId: SpriteId): { w: number; h: number; anchor: { x: number; y: number } };
  frameAnchor(spriteId: SpriteId, frame: string): { x: number; y: number };  // mirrored frames differ
  mount(spriteId: SpriteId): { x: number; y: number } | null;                // tower bases
}
```

`variant` defaults to `default`. Anims loop unless their definition sets `loop: false` (fire, bursts). The code is the home of the interface: `src/render/sprites/SpriteSource.ts`.

`CodeSpriteSource` is the only implementation for now. `BootScene` bakes and registers it synchronously at boot (`register(scene)`) and stores it in the game registry under `spriteSource`. A future `SheetSpriteSource` would load a PNG atlas plus JSON (for example an Aseprite export) whose frame names follow the same contract, with anchors coming from the same sprite registry. Swapping is then one line in `BootScene`, and sprites can be migrated one at a time because a composite source can try sheets first and fall back to code.

The baked RGBA buffers are also available to the DOM UI (portraits and icons) as canvases, so the HUD and Phaser share one art pipeline.

### The sprite gallery

`gallery.html` (built alongside the game, entry `src/app/gallery.ts`) shows every registered sprite as a labeled card: each palette variant's frames at 1× and at an integer zoom (3× up to 20 px, else 2×), on dark (`ink.0`) and light (`steel.4`) backgrounds, with the `default+…` derived variants and the default frames composited with their `@glow`. Above the cards, small **dioramas** of an A1M1 corner place tiles, props, towers (heads on mounts), enemies, and VFX by their anchors with depth sorting, once in `act1` at 2× and once per environment palette at 1×, each over its env's sky gradient (stepped bands, ordered-dithered seams) and `shade`, with ground enemies on their contact shadows. The page is deterministic (no time, no randomness, no running animations).

The `smoke/gallery.spec.ts` smoke test opens it at a 1600 px wide viewport, checks the `data-*` counters on `<body>` (sprite count equals the registry; every displayed frame rendered), and writes the full-page screenshot to **`test-results/gallery/gallery.png`**, the milestone art-trail artifact.

## Open questions

1. **More than one raised level.** §1 supports a single high-ground level. If design/maps.md wants stacked levels or ramps that enemies walk up, depth sorting needs a z-aware rule.
2. **Finale room.** If the finale outgrows 22×14 ([design/maps.md, open questions](../design/maps.md#open-questions)), choose between panning for that map alone and a 24×12-style aspect that keeps `cols + rows ≤ 36`.
