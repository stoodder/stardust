# Conventions

How to write code and content for Stardust, and how to prove it works. The module layout and the sim/render split are in [architecture.md](architecture.md). The workflow that runs these checks is in [CLAUDE.md](../../CLAUDE.md) (step 5, the test loop). **This doc is the detailed home of the test loop.**

---

## TypeScript style

**Compiler options** (`tsconfig.base.json`): `strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `noImplicitOverride`, `noFallthroughCasesInSwitch`, `verbatimModuleSyntax`, `isolatedModules`, `erasableSyntaxOnly`, `allowImportingTsExtensions`, `noEmit`, `module: "esnext"`, `moduleResolution: "bundler"`, `target: "es2023"`.

Rules:

- **No `any`.** Use `unknown` and narrow it. `as` casts are allowed only at validated boundaries (content compile, save load), with a comment. A non-null `!` needs a comment saying why it's safe.
- **Erasable syntax only:** no `enum`, no `namespace`, no constructor parameter properties. Use `as const` objects and string-literal unions. (This is what lets Node run `.ts` files directly.)
- **Discriminated unions** for commands, events, behaviors, abilities, and dialogue nodes, with an exhaustive `switch` ending in `assertNever(x)`.
- `interface` for object shapes, `type` for unions and aliases.
- **Named exports only**, no default exports. The only `index.ts` barrels are module public APIs (`src/sim/index.ts`) and content registries.
- **Relative imports with the `.ts` extension**, `import type` for type-only imports, and no path aliases ([architecture.md §5](architecture.md#5-build-test-and-deploy)).
- **Pure modules** (`sim`, `content`, `story`, `shared`) have **no module-level mutable state**. Everything lives in an explicit state object, so many sims can run in one process.
- Functions and plain data in pure modules. Classes are fine where the framework wants them (Phaser scenes, views).
- Content and compiled definitions are `readonly`. The sim exposes its state as `DeepReadonly<SimState>`.
- **Units go in the name** wherever a number has a unit: `rangeTiles`, `ratePerSec`, `speedTilesPerSec` in content, and `cooldownTicks` and `speedTilesPerTick` in compiled sim data (the tile is the sim's distance unit). Credits, HP, and damage are integers.
- Comments explain *why*, not *what*. Public functions of a module get a one-line TSDoc.

## Naming

| Thing | Style | Example |
|---|---|---|
| Code file (module of functions) | `camelCase.ts` | `rasterize.ts`, `applyCommands.ts` |
| File whose main export is a class or component | `PascalCase.ts(x)` | `BattleScene.ts`, `BuildBar.tsx` |
| Content file | `<id>.ts` (snake_case, matching the id) | `towers/example_blaster.ts` |
| Unit test | next to the source, `*.test.ts` | `path.test.ts` |
| Smoke test | `smoke/*.spec.ts` | `smoke/battle.spec.ts` |
| Types and interfaces | `PascalCase` | `SimState`, `TowerDef` |
| Functions and variables | `camelCase`, functions start with a verb | `spawnEnemy`, `towerAt` |
| Booleans | `is` / `has` / `can` prefix | `isAlive`, `canAfford` |
| Constants | `SCREAMING_SNAKE` | `TICK_HZ`, `TILE_W` |
| Content ids | `snake_case`, unique per kind | `example_blaster`, `a1_m01` |
| Map ids | `a<act>_m<nn>`, with `fin_m<nn>` for the finale and `ch_<name>` for challenge maps | `a1_m01`, `a3_m04` |
| Sprite ids | `<category>.<id>` | `enemy.example_mite`, `icon.tower.example_blaster` |
| Story flags | `snake_case`, declared in `content/dialogue/flags.ts` | `spared_quiet_wave` |
| Events and commands | `PascalCase` event names, `camelCase` command types | `EnemyDied`, `{ type: 'build' }` |

## File layout

- **One definition per content file**, registered in that folder's `index.ts`. Never use `import.meta.glob`. Registries are explicit so that Node can load them.
- A system or behavior gets its own file in `sim/systems/`, `sim/behaviors/`, or `sim/abilities/`, with its test beside it.
- Keep files under about 300 lines. Split by responsibility, not by layer.
- Nothing outside a module imports another module's internals. Cross-module imports go through the allowed edges in [architecture.md §4](architecture.md#4-other-modules).

## Recipes

Every recipe ends with **the test loop** (below) and **updating the docs** (CLAUDE.md step 7). The example ids are illustrative; real rosters live in the design docs.

### Add a tower

1. **Confirm the design.** The tower must exist in [design/towers.md](../design/towers.md) (role, tiers, specializations, unlock). If it doesn't, stop and ask the orchestrator; don't invent towers.
2. **Sprites** in `src/content/sprites/towers/<id>.ts`: a base with `t1`, `t2`, `t3`, `spec_a`, and `spec_b` frames; a head with at least SE and NE facings (mirrored to 4); a `fire` animation; and a 16×16 `icon.tower.<id>`. Add a projectile sprite in `sprites/projectiles/` if the tower needs a new one. Register them in `sprites/index.ts`. Format: [art/tech-spec.md §2](../art/tech-spec.md#2-code-generated-pixel-art-format).
3. **Data** in `src/content/towers/<id>.ts`. The shape is `TowerDef` in [`src/content/types.ts`](../../src/content/types.ts).
   ```ts
   export const exampleBlaster = defineTower({
     id: 'example_blaster',
     name: 'Blaster',                                         // the display name every screen shows
     faction: 'everglow',
     role: 'Single-target DPS',
     sprites: { base: 'tower.example_blaster', head: 'tower.example_blaster_head', icon: 'icon.tower.example_blaster' },
     tiers: [
       { cost: 100, targets: { ground: true, air: false }, defaultPriority: 'first',
         attack: { kind: 'projectile', projectile: 'projectile.rivet_small', speedTilesPerSec: 8,
                   type: 'kinetic', damage: 6, ratePerSec: 1.6, rangeTiles: 2.5 } },
       { cost: 80,  attack: { damage: 9 } },                  // later tiers patch the previous tier
       { cost: 140, attack: { damage: 14, rangeTiles: 2.75 } },
     ],
     specs: {                                                 // tier 4: one R&D purchase unlocks both
       a: { name: 'Overcharge', cost: 300, attack: { damage: 30, ratePerSec: 0.8 } },
       b: { name: 'Rapid',      cost: 300, attack: { ratePerSec: 4 }, effects: [{ status: 'chilled', pct: 0.1, durationSec: 1 }] },
     },
   });
   ```
   Tiers 2 and 3 patch the tier before, and specs patch tier 3 (`compileContent()` resolves them; the merge rule is in `src/content/compileCore.ts`). A tier may also change `targets` or `defaultPriority`. Numbers come from towers.md. Modifiers stack by the design formula (flat first, then summed percentages; see [architecture.md §2](architecture.md#sim-public-api)).
4. **Register** it in `src/content/towers/index.ts`. Its synergy links (towers.md §6.2) go in `src/content/links/<link>.ts` via `defineLink({ id, name, partners: [{ tower, bonuses }, { tower, bonuses }] })` (`LinkDef` in `types.ts`), registered in `links/index.ts` (append: registry order is each link's bit).
5. **New behavior?** If the attack `kind` doesn't exist yet, add its variant to `AttackDef`, a `FEATURE_GATES` row naming the task that will run it (`src/sim/gates.ts`), and `src/sim/attacks/<kind>.ts` (the towers system routes the kind there, as it does `chain`), and write `<kind>.test.ts` (damage, cooldown, range edge cases, targeting modes, jammed state, hold fire, determinism).
6. **New visuals?** Add the projectile handling in `render/views/ProjectileView.ts` (a beam's is `render/views/BeamView.ts`), following [art-direction.md §7](../art/art-direction.md#7-vfx).
7. **Unlock** it through progression content (`content/upgrades/`), per [design/progression.md](../design/progression.md).
8. **Test loop:** `npm run check`. While tuning, run `npm run sim -- --map <id>` for each map whose builds or reference profile include the tower.

### Add an enemy

1. **Confirm the design** in [design/enemies.md](../design/enemies.md): abilities, counters, and **tell ids** from the vocabulary in [art-direction.md §8](../art/art-direction.md#8-readability-and-enemy-ability-tells). A new kind of tell must be added to that table first.
2. **Sprites** in `src/content/sprites/enemies/<id>.ts`: SE and NE walk cycles (mirrored to 4 facings), the faction palette, and a death animation (or the faction's shared one; Skitterkin death VFX vary by act).
3. **Data** in `src/content/enemies/<id>.ts` via `defineEnemy({ id, name, faction, body, layer, hp, armor, shield?, speedTilesPerSec, leak, bounty, spawnIntervalSec, traits: [...], tells: [...], sprites })` (`EnemyDef` in [`src/content/types.ts`](../../src/content/types.ts)). Column meanings and numbers come from the roster tables in enemies.md.
4. **New ability?** Add its shape to `EnemyDef` (one optional field per ability: `burrow`, `split`, `huddle`, `boss`, …), a `FEATURE_GATES` row until it runs, then `src/sim/enemyAbilities/<kind>.ts` (called from the `enemyAbilities` system) as a state machine (`idle → telegraph → active → cooldown`), with the telegraph time as data, and implement interrupts (Stasis, Unnerved) per [design/enemies.md §2.4](../design/enemies.md#24-status-effects). **Jamming** must follow [design/enemies.md §4](../design/enemies.md#4-tower-disabling-jamming): its minimum tell, maximum duration, post-jam immunity, and exhaustive source list (a new jammer needs a decision entry). `content/validate.ts` enforces the numeric limits from `content/rules.ts`. Write tests for the full cycle, including interrupts, and that a jam never removes or damages a tower.
5. **Codex entry** in `src/content/codex/<id>.ts` (voice per [story/style-guide.md](../story/style-guide.md)).
6. **Register** it, add it to waves, and run `npm run check`, plus `npm run sim -- --map <id>` for every map whose waves include it.

### Add a map

1. **Confirm the design:** [design/maps.md](../design/maps.md) (tile legend, layout intent, per-act targets, the one new thing this map introduces) and [story/campaign.md](../story/campaign.md) (beats, unlocks, companion, choices). Add the map id to `content/campaign.ts` in campaign order.
2. **Create `src/content/maps/<id>/`** with four files. Together they form one `MapDef` ([`src/content/types.ts`](../../src/content/types.ts)). The id and values below are illustrative; they are not A1M1's.
   - **`map.ts`**: layout and rules.
     ```ts
     export const map = defineMapLayout({
       id: 'example_map', act: 1, env: 'act1', objective: 'defend',
       size: { cols: 10, rows: 5 },
       // prettier-ignore
       tiles: [                     // legend: design/maps.md §3 (# path, o pad, ^ high ground,
         '..........',              //   + power node, x wreckage, . decor, S spawn, C core)
         'S####oo^..',
         '.oo.#o..x.',
         '..+.#####C',
         '..........',
       ],
       paths: [{ id: 'a', tiles: [[0,1],[1,1],[2,1],[3,1],[4,1],[4,2],[4,3],[5,3] /* … */, [9,3]] }], // S, every #, C (maps.md §4)
       markers: { peeker: [1, 0] },                       // named decor tiles for scripts
       underWreckage: { '8,2': 'o' }, salvage: { '8,2': 40 },
       startCredits: 300, coreIntegrity: 20, stardust: 0,
       towerUnlockWave: { example_mortar: 3 },            // unlocks when W3's countdown starts
       threatIntel: ['fast'],                             // every trait in waves.ts
       requiredCounters: [],                              // A1M1 requires none; ≤ 3, each with a noCounterBuild
       medals: { challenge: { id: 'one_mortar', name: 'Mortar Minimalist',  // required on campaign maps
         description: 'Win with at most one mortar.', condition: { towers: { tower: 'example_mortar' }, lte: 1 } } },
       objectives: [{ id: 'clean_w4', name: 'Clean Sweep', description: 'Lose no integrity.',  // optional; Objective Intel
         condition: { stat: 'integrityLost', lte: 0 }, intel: 1 }],
       companion: { id: 'bricks', state: 'present' },     // or { pick: [...] }, or null
       events: [{ id: 'w03_radio', on: { wave: 3, phase: 'start' }, actions: [{ cue: 'example_map_w03' }] }],
     });
     ```
   - **`waves.ts`**: `defineWaves([...])`, one entry per wave (`countdownSec` defaults by act) with its groups: `enemy`, `count`, `route` (a path, air-lane, or rift-lane id, which also fixes the spawn), and optionally `intervalSec` (default: the enemy's `spawnIntervalSec`), `delaySec`, and `tags`.
   - **`builds.ts`**: `defineBuilds({ ... })` with `referenceProfile`, `parBuild`, `noCounterBuilds` (one per required counter), `altBuilds` (at least 2 from A1M4), and optionally `flagVariants` and `guards` (see [Balance sims](#balance-sims-npm-run-sim)).
   - **`index.ts`**: `export const exampleMap = defineMap({ ...map, waves, ...builds })`.
3. **Register** the map in `src/content/maps/index.ts`. The content test runs every check in [architecture.md § Validation](architecture.md#validation): geometry, threat intel and required counters, the new-threat limits, revisit rules, builds, and the par-purchasable check.
4. **Dialogue cues and scripts:** map `events` are triggers with actions ([story-runtime.md § Map scripts](story-runtime.md#map-scripts-story-driven-sim-changes)); a `cue` action emits an id (`<map_id>_wNN` for wave cues) that story content binds to a scene or bark (next recipe). Story moments that change play (revocation, pivot, forced input, clickable objects, allies, timers, checkpoints) are script actions too, never special-case code. If a script reads a story flag, add a `flagVariants` entry to `builds.ts` for each value that changes the sim.
5. **A story map's extras** (the worked examples are `a1_m03`–`a1_m05`; the map's act-file entry under `docs/story/campaign/` says which it needs):
   - **Dialogue:** a folder `content/dialogue/a<act>/<map_id>/` with `scenes.ts` (the `_brief` briefing, `_wNN` radio, `_cue_*`, `_debrief` with a `lost` branch, any `_scene_*`) and `barks.ts`, registered in `MAP_DIALOGUE` (next recipe). Lines are verbatim from the act file; once every line is in, add the map to `COMPLETE` in `tools/dialogueCanon.test.ts`.
   - **Objectives:** `objectives` in `map.ts` (above; [design/core-loop.md §2.13](../design/core-loop.md#213-optional-objectives)); the campaign's Objective Intel is capped by validation. Medals and objectives may only use condition atoms the sim tracks (`ConditionDef` in `types.ts`).
   - **A boss:** an enemy with a `boss` field (phases, `ending: 'driveOff'` or `'retreat'`; [design/enemies.md §6](../design/enemies.md#6-bosses)) in its own wave, with every unit that must stay in another wave (a `driveOff` takes the boss's whole wave). Phase dialogue uses the `bossPhase` / `bossHpPct` triggers in `events`. A capstone boss built from known traits isn't a new threat.
   - **Routes:** a second spawn is another path; an air lane (`airLanes`) must end on the core.
   - **Companion and allies:** `companion` names who is in slot 2 (their ability's `companion` field must match); an ally post (`allies`) stands on a decor `marker`.
   - **Props and the Peeker:** a decor marker named in `DECOR_MARKERS` (`render/views/groundTiles.ts`) draws its prop; a prop that arrives with a cue goes in `CUE_DECOR`; a `peeker` marker places the Peeker (Act I).
   - **Around Results:** scenes before and after the card, and story stamps, go in `content/dialogue/resultsFlow.ts`.
   - **Story flags read by scripts** get `flagVariants`; a medal-exempt story wave (a `quiet_wave` group) gets the harness's Hold Fire run (#16a) automatically; an R&D pick that should matter goes in `rndPickChanges`; the medals par must earn go in `parMedals`.
   - **Base and codex:** the map's memos (`content/memos/`), codex entries (`content/codex/`), and anything it issues or stocks (`availableAfter` in `content/upgrades/`), and a dev save after it in `meta/__fixtures__/devSaves.ts` ([meta-runtime.md § Dev saves](meta-runtime.md#dev-saves)).
6. **Tune** with `npm run sim -- --map <id> --report` until it passes. Read the per-wave leak table, the per-tower damage, and the link-uptime column, not only the verdict.
7. **Test loop:** `npm run check`. The "every map boots" smoke test picks up the new map automatically. Look at its screenshot.

### Add dialogue

1. **Read** [story/style-guide.md](../story/style-guide.md) (format, voice, tone per act, length limits), [story/characters.md](../story/characters.md) (speaker voices), and the map's beat in [story/campaign.md](../story/campaign.md).
2. **Scenes** go in the map's `src/content/dialogue/a<act>/<map_id>/scenes.ts` (`defineScene`, a list of `line` / `choice` / `branch` / `set` / `end` nodes; ids per style-guide §5.3, and the id's slot decides when it plays: `_brief`, `_wNN`, `_cue_<name>`, `_debrief`, `_scene_<name>`, `_base_<name>`; [story-runtime.md § Dialogue runner](story-runtime.md#dialogue-runner)). **Map barks** go in the same folder's `barks.ts` (`defineBarks`, each with a trigger from [design/core-loop.md §6.3](../design/core-loop.md#63-barks), a `when`, and a once or cooldown rule); barks for several maps go in `src/content/dialogue/barks/`. A new map's folder is listed once: an Act I map's in `content/dialogue/index.ts` (`MAP_DIALOGUE`), a later act's in its act file (`content/acts/a2.ts`, `a3.ts`, `fin.ts`; [architecture.md § 5, *Lazy chunks*](architecture.md#5-build-test-and-deploy)). **Memos** (`content/memos/`), **codex entries** (`content/codex/`), Bricks's **name tags** (`content/dialogue/tags.ts`), and the **scenes and stamps around Results** (`content/dialogue/resultsFlow.ts`) have their own files.
3. **Bind** it to a trigger: a map `cue`, a bark trigger, or a menu event. An optional bark button ("Who's there?") is a `button` on the bark ([story-runtime.md § Barks](story-runtime.md#barks)); it never blocks play.
4. **New flags** are declared in `src/content/dialogue/flags.ts` with a type and a one-line description, so typos fail validation. Flags derived from play (like `spared_quiet_wave`) are run-end rules in the same file.
5. Speakers and portrait expressions must exist (the content test validates them). Use the tokens in [story-runtime.md § Text substitution](story-runtime.md#text-substitution) (`{name}`, `{callsign}`, pronouns, `{v:are|is}`, `{pests_processed}`, `{evacuated}`, `{glyph:sun}`); never hard-code the protagonist's name, pronouns, or callsign. QUILL's directive lines use "(Per policy.)" and the `policy` expression together. Silence is a line with `text: ''` and `durationSec`.
6. The content test enforces the rules in [story-runtime.md § Validation](story-runtime.md#validation): lengths after worst-case substitution, the protected `{name}` rule, QUILL's tell, and the exclamation budget. If a line fails a length check, split it into two lines; don't raise the limit.
7. **Test loop:** `npm run check`. If the change adds a choice or a new node kind, add a story runner test and extend the dialogue smoke flow, then look at the screenshots.

## The test loop

Run this after implementing and **before any review** (D002). It's also re-run after every round of review fixes, and once more before shipping a milestone. **The loop is done only when everything is green.**

### What to run

| Change touches | Run |
|---|---|
| A task's code in `src/`, configs, or `tools/` (a subagent's own gate) | **`npm run check:fast -- <smoke specs…>`** (the per-task gate, D148): every step but `smoke` runs whole, and `smoke` runs only the specs named, which are the task's own specs and the flows its change touches. A task that changes shared infrastructure (`tools/`, configs, the smoke harness, BattleScene's wiring) runs the whole gate instead |
| A wave's integrated tree, review-round fixes, and the milestone's ship | **`npm run check`** (the whole gate), run by the orchestrator |
| Docs only (`docs/`, `CLAUDE.md`, `tasks.md`, `.claude/`) | **`npm run check:docs`**, plus the manual consistency pass below |
| Inner loop while coding | `npm run test`, `npm run sim -- --map <id>`, `npm run smoke -- -g <flow>`. These are shortcuts, not a gate. |

`npm run check` (`tools/gate.ts`) runs, in this order (fail fast): **`typecheck` → `lint` → `test` → `build` → `smoke` + `sim` (side by side) → `check:docs`**, then prints each step's time against its share and the gate's wall time against the **8-minute budget** ([Gate time](#gate-time)). `npm run check:fast -- <specs…>` runs the same phases with `smoke` cut to the named specs (skipped when none are named) against a 5-minute budget. `smoke` streams its output; `sim`'s prints when it ends. The scripts are defined in [architecture.md §5](architecture.md#5-build-test-and-deploy). Run it in the background: it outlasts the 2-minute default command timeout.

**Run one `npm run check` at a time** per checkout: parallel runs (two agents, say) share `dist/` and the smoke server's port 4173, so one run's build or server breaks the other's smoke step. `npm run smoke` on its own tests whatever `dist/` holds now, so run `npm run build` first. Three variables (`playwright.config.ts`, `smoke/out.ts`) keep an agent's runs apart from another's in the same checkout: `SMOKE_PORT=<n>` moves the smoke server to another port; `SMOKE_OUT=<dir>` sends Playwright's output (screenshots, the gallery's sheets, failure context) to a private folder instead of `./test-results`, which each run cleans first; `SMOKE_DIST=<dir>` serves a private build (`npx vite build --outDir <dir> --emptyOutDir`) instead of `dist/`, for a targeted `npm run smoke -- <spec>` while another agent's gate builds. The gate itself always builds and serves `dist/`.

### Red means stop

- Fix the cause. **Never weaken, skip, `.only`, or delete a test, loosen a balance band, or add a console allow-list entry just to get green.** If a band or expectation is genuinely wrong, change it deliberately, say why in the commit message, and get it past the gameplay reviewer.
- If you can't get to green within the task's scope, mark the task `[!]` in your report and say exactly what's failing.

### Gate time

The whole gate's budget is **8 minutes** of wall time, under the 10-minute command cap (D137). `tools/gate.ts` holds the budget and each step's share and, after every `npm run check`, prints a table of each step's time against its share and the total against the budget. The steps run in phases, one after another, except `sim`, which runs beside `smoke`: smoke's browsers leave cores idle while flows wait on real-time beats, and the harness fills them. A step over its share prints a warning, not a failure: wall time is noisy when other agents share the machine, and a red gate must mean broken code. **Read the table on every run.** The task that pushes a step over its share brings it back (with the levers below) or reports it as a follow-up.

**The gate is CPU-bound.** On the 4-core cloud session the cores are 93–99% busy through `test` and `smoke`: about 2,100 CPU-seconds of work at M6 content (smoke ~1,600, test ~320, sim ~120). Running more steps side by side only helps where a step leaves cores idle (`sim` beside `smoke` saved ~25 s; typecheck and lint beside `test` cost more than they saved, T764), so the gate's time falls only when a step does less work.

| Step | Share | Measured (4 cores; quiet = no other agent's load). M6 content (14 maps, 244 flows), quiet, 2026-11-11 (T764): **524–550 s** (563 s before T764) | Guardrail |
|---|---|---|---|
| `typecheck` + `lint` | 10 s + 20 s | 5 s + 10 s warm (`lint` 24–29 s when Prettier's cache is cold). `lint`'s Prettier half is cached (`--cache`, [architecture.md §5](architecture.md#5-build-test-and-deploy)), so a warm run is mostly oxlint's | — |
| `test` | 85 s | 80–81 s quiet (~320 CPU-s): the balance files are ~180 s of it (A3M3's alone ~43 s), import ~32% | See **The `test` step** below |
| `build` | 5 s | 1–2 s, the initial-JS check included (~0.1 s): **786 kB** gzipped (T802) | The initial JS, gzipped, warns over 800 kB and fails the step over 900 kB, or when an initial script holds a lazy act (`tools/bundleSize.ts`, [architecture.md §5](architecture.md#5-build-test-and-deploy)) |
| `smoke` + `sim` | 420 s + 90 s (side by side) | smoke 427–438 s with sim beside it (436 s alone before T764); sim 99–129 s beside smoke (31 s alone). 3 workers 438 s, 4 workers 427 s (one quiet run each) | See **The `smoke` step** below; the harness's maps run in parallel ([Sim time](#balance-sims-npm-run-sim)), and a map's runs are bounded by assertion 13 (CPU time, so load beside it doesn't trip it) |
| `check:docs` | 5 s | 0.2–0.4 s | — |

**At M7 content plus M8's seams** (17 maps, 318 flows; quiet, 2026-11-11, after T766) the whole gate took **686 s** (749 s before T766), over its budget: typecheck 6 s, lint 11 s, test 109 s, build 1 s (the initial JS **888 kB** gzipped), smoke 559 s and sim 124 s side by side, check:docs 0.2 s. An overrun is a warning, not a failure (D147, D148): each task runs `check:fast`, and the whole gate runs per wave and at the milestone. No balance file passes 60 s (A3M3's is the longest, ~46 s), so none is split; the `test` step is bound by its total work (~295 s of test time on 4 workers), not one file. The sim spreads each map's runs over its workers ([Sim time](#balance-sims-npm-run-sim)), so the finale's runs share the cores, and a heavy map's balance tests split across files (*The `test` step*, below).

**The `test` step.** Vitest runs two projects (`vite.config.ts`). Module import, not the tests, was two thirds of the step: an isolated file re-evaluates the whole content graph (maps, sprites, dialogue). So most files run in the **`shared`** project (`isolate: false`: one module graph per worker, reused across files), and a test must leave module state as it found it: restore fake timers (`vi.useRealTimers()`), unstub globals (`vi.unstubAllGlobals()` in `afterEach`), reset what it sets. A file that mocks modules (`vi.mock`, `vi.doMock`, `vi.resetModules`), or that needs its modules' first evaluation, runs in the **`isolated`** project; `vite.config.ts` finds them by reading the files, and a file opts in with a `// vitest: isolate` comment. A test that passes alone and fails in the full run is leaking state: fix the leak (`npx vitest run --sequence.shuffle.files --sequence.seed=<n>` reproduces order effects). The balance test files (`src/balance/<map>.test.ts`) are the heaviest work: each re-runs a whole map's harness per robustness shift. Shift several waves at once (a *compound* shift, `src/balance/__fixtures__/shifts.ts`: `shiftedContent`, `bothWays`, `judgeShift`), so a file runs its tuned harness once plus about 2–6 shifted ones (A1M4's 6 is the most, T460); one harness run per test, so `HARNESS_TEST_TIMEOUT_MS` (60 s) holds under load; use `runMap(…, { seeds: 1 })`, filter with `build:`, or a single `runHeadless` when a shift concerns one build. **A map whose tuned harness passes ~30 s in one file splits it across files**, one part each (`<map>Part<n>.test.ts`): `runMap(content, id, { seeds: 1, part: { index, count } })` runs part `index` (from 0) of `count` (`partSpecs` in `src/balance/harness.ts`): a build's checks stay together, the map-level ones go in part 0, and each part runs only the runs its checks need (a run two parts need runs in both). The parts together hold every check once, each judged as the whole map judges it (`src/balance/harnessSplit.test.ts`), and each part makes the run-level checks (steps, #12, #13) over its own runs. A compound that fails where each part alone passes is a finding (report it), not a reason to drop the shift. Vitest runs files in parallel on one worker per core (`maxWorkers: '100%'`: its default leaves a core to its main thread, which only waits), longest first from its cache, so the total and the longest file (A3M3's) both bound the step. The default per-test timeout is 20 s (`testTimeout`), so heavy pure tests hold under load.

**The `smoke` step.** Its work is **drawing and boot**. Headless Chromium draws in software (SwiftShader): before T564 an idle page cost its GPU process 2–3.7 cores at 60 fps, so two workers' pages starved each other, and a screenshot took ~1 s under load. Each test also opens a fresh page, and a boot takes ~1.5–2 s of CPU (most of it baking the sprites), so a flow that navigates three times pays for it three times. A whole map fast-forwarded one tick at a time (the map flows' `until` loops) costs only ~1 s, so a map flow needn't start mid-map. The levers, in order:

- **Boot once per test.** Reach a state with `save=<id>`, `map=<id>` and the `__sd` hooks (`goto`, `results`, `dialogue.play`) rather than another `page.goto` or `reload`, unless reloading is the point.
- **Keep boot cheap.** A boot was ~1.3–1.7 s of main-thread CPU at M6 (T764), and much of it is sprites: the bake (~0.2 s) and handing the atlas pages to Phaser (~0.15 s). Portraits cost a boot nothing (T766): `definePortrait` paints a portrait the first time its frames are read, and the atlas leaves them out (`ATLAS_SPRITES`), since only the DOM draws them, so a page paints and bakes just the speakers it shows (~0.2 s of painting and ~600 atlas frames saved). The atlas pages are CPU-backed canvases (`willReadFrequently`, `render/sprites/CodeSpriteSource.ts`; a unit test holds it): GPU-backed pages cost ~0.8 s a boot. Each page is composed in memory and put once, and `colorize` looks each palette code up once per image (T764: ~0.2 s off a boot). Anything new baked at boot (a texture, a big canvas) is measured the same way: `performance.now()` around it, or the CPU profile of one boot.
- **No real time a flow doesn't need.** Play out waves with `fastForward`; use real frames only for a beat a screenshot or assertion needs; story flows that wait on the radio or a scene use `fasttext=1` ([Browser smoke tests](#browser-smoke-tests-npm-run-smoke)); a fixed `waitForTimeout` is for a real-time animation only, with a comment naming it. One flow stays under about 10 s; Playwright lists every spec file over 15 s at the end of the run (`reportSlowTests`).
- **The browser.** In a cloud session (`CHROME_PATH` set) the config runs the preinstalled Chrome Headless Shell, the same kind of browser CI's headless Playwright uses: with the CPU-backed atlas it cut a boot-heavy subset's work by ~27% against full Chrome (T501j). `SMOKE_CHROME=<path>` picks another.
- **Draw less.** An idle battle page draws for about a core at 30 fps, nearly all of it SwiftShader rasterizing the WebGL canvas in the GPU process. The browser composites in software (`--disable-gpu-compositing`, `playwright.config.ts`; `SMOKE_GPU_COMPOSITING=1` puts SwiftShader compositing back), and the shared fixture caps the page at **30 fps** (`capFrames` in `smoke/fixtures.ts`, an init script over `requestAnimationFrame`; `SMOKE_FPS=<n>`, 60 or more for no cap). Neither changes what a flow sees: the sim runs on elapsed time, not frames, and a screenshot shows the same frame (pixels within a level or two of the GPU compositor's). Together they cut a 58-flow subset's CPU by 37% (577 s to 362 s) and a screenshot from ~1 s to ~0.3 s under load (T564). A test whose work runs off the frame loop (the audio's offline renders) calls `holdFrames(page)` (`smoke/hooks.ts`) after boot, so the idle canvas stops drawing; nothing that waits on a frame moves while held. A spec that installs Playwright's clock gets the clock's frames instead (60 fps). Don't cap lower than 30: at 20 fps a frame needs 3–5 ticks, and the host's catch-up cap (4 a frame, `app/host.ts`) drops the rest under load, so the sim falls behind real time and real-time flows fail (T764: A3M1's Maw line).
- **Workers:** `SMOKE_WORKERS` (a count or a share such as `50%`), default three quarters of the cores (3 on 4). Once a page drew less (above), 3 workers beat 2 quiet and under load (T564: 284 s quiet for 179 flows); before, each worker's GPU process took one to two cores and 3 ran no faster than 2 (T501j). 4 workers ran 11 s faster than 3 in one quiet gate each (T764: 427 s against 438 s for 244 flows, within the noise), and leave nothing idle for a loaded machine, so the default stays 3. Re-measure before changing it.
- **Split a long spec.** Playwright lists every spec file over 15 s; a single test of a minute or more is a long pole and nears its timeout under load. Split its work into independent tests the workers share out: the sprite gallery captures its sheets in three parts (`smoke/gallery.spec.ts` `PARTS`; an 8,000 px sheet is ~6 s of software raster and PNG encoding).

New flows start from a dev save or `map=<id>` rather than playing earlier maps through. A map task adds one normal-flow step from the star map, not a play-through of the act.

### Unit and sim tests (`npm test`)

Vitest, Node environment, tests next to the source. It covers everything listed under [Testing](#testing), including the content validation test, the determinism test on a fixture map, save migrations, and the architecture boundary test. Its time is the `test` row of [Gate time](#gate-time).

### Balance sims (`npm run sim`)

`tools/sim.ts` is the CLI over `src/balance/`. It loads the content in plain Node and runs each map's scripted builds headlessly through `runHeadless()` ([architecture.md § Sim public API](architecture.md#sim-public-api)). With no arguments it checks **every map in campaign order**. Use `--map <id>` while tuning (it skips assertion 3, which needs the earlier maps), `--seeds <n>` to run the every-seed assertions on seeds 1–*n* (the seeds 1–3 ones use 1–min(3, *n*)), `--build <name>` to keep only the assertions about one build (`par`, `none`, `alwaysCallEarly`, `parNoAbilities`, `spareFleeing`, `holdFireWhile:<tag>`, an alt build's name, a `requiredCounters` category, a guard's name, or an R&D pick's upgrade id) plus the runs they compare against, `--jobs <n>` to run on *n* worker threads (default: one per core; `--jobs 1` runs everything on the main thread), and `--report` to write `reports/balance.{json,md}` (gitignored).

The **design rules** behind these assertions (par margins per act, monotonic difficulty, counters matter, the forgiving floor, the jam limit, fair early calls, meta can't replace counters) are owned by [design/maps.md §6](../design/maps.md#6-difficulty-curve) and [§6.4](../design/maps.md#64-balance-harness). This section defines how the harness checks them. **"Par build" and "reference strategy" mean the same thing.** Which assertions run today, and which are refused until their maps, is architecture.md's *Built so far* note ([architecture.md](architecture.md#architecture)).

The **par-purchasable** check (every par build's reference profile can be bought by that point in the campaign) is static, so it runs in the content test, not here ([architecture.md § Validation](architecture.md#validation)).

**How the harness judges** (`src/balance/mapChecks.ts` assembles each map's checks from the families in `parChecks.ts`, `counterChecks.ts`, `altChecks.ts`, and `freeChoiceChecks.ts` over the kit in `checks.ts`; `refusals.ts` and `harness.ts` do the rest; the numbers live in `src/balance/rules.ts`):

- **Margin** is integrity left ÷ max integrity × 100 for every run, so a loss is 0. Max integrity is what the run starts with after its modifiers (Reinforced Core's ranks, Story's 30). On a Protect map it is the lower of that and asset left ÷ max asset × 100 (`marginOf` in `checks.ts`), and the per-wave tallies carry the asset's losses (`assetLost`).
- **Run labels** name a build and, after `@`, the profile it runs on when that isn't the reference profile on Standard: `par@story` (assertion 9), `noCounter:<category>@fullCatalog` (assertion 6), and `par@rnd:<upgrade id>` (the `rnd` check). The first two keep the build as their subject, so `--build par` or `--build armor` keeps them; the `rnd` checks' subject is `rnd:<upgrade id>`.
- **Assertion 6** runs each no-counter build on the full-catalog profile (seeds 1–3) and passes on any loss. Its summary lists the catalog grants the sim doesn't simulate yet, which the profile leaves out (none since wreckage landed; see *Profiles* below). It never runs for `jam`: the jam limit caps what jamming can take below what the full catalog adds ([maps.md §6.4](../design/maps.md#64-balance-harness); D146 addendum, T760), so #5 holds no-jam to losing on the reference profile instead. A map's `counterExemptions` (`BuildsDef`: each a counter, `jam` or `detection`, with its reason and `pinnedBy`, the balance test that pins what the counter's absence costs instead, through `expectCounterCost`: par's margin over the no-counter build's, at least `COUNTER_COST_MIN_POINTS`, 10) skip #5's loss and #6 for that counter, while #5's premise check (the build carries no answer) still runs (`counterChecks.ts`); the rule and the maps that use it are [maps.md §6.1](../design/maps.md#61-per-act-targets)'s.
- **Assertion 9** runs par on Story (seed 1) and compares it with the median of par's Standard margins over every seed.
- **Assertion 5's "before the final third"** means the last wave started when the map is lost is ≤ ⌊⅔ × waves⌋. Its premise is checked too (`counterChecks.ts`, needing no run): the no-counter build carries no answer to its category, judged by the same model as the content validator (`src/content/counterAnswers.ts`: the tiers and specs its towers reach, from where, and the abilities it casts; [design/enemies.md §3.1](../design/enemies.md#31-counter-categories)). **Placement counts:** a placed tower answers a category only if one of its placements can reach a route that category's enemies take (the tile's distance to the route's polyline ≤ the longest attack range it reaches × 1.25 on high ground, + `REACH_SLACK_TILES` 0.5 for the small range bonuses the model doesn't track). So A1M3's no-air build may keep Rivets out of the air lane's reach. A loadout tower the build never places, and a tower with no attack range, still count; neutral units (Gerald) are in no category.
- **Assertion 7** also requires `alwaysCallEarly` to **win**. When par's margin is within 10 points of 100 on every seed (par ≥ 90 in Act I), the cap is 100 and the fairness bound can't fail, so the summary says so ("the fairness bound is vacuous; only the win is checked") rather than passing silently.
- **Abilities matter** (check `abilities`): when the par build casts a commander ability, the par build with its `ability` steps removed (`parNoAbilities`; the slot stays equipped) must end with a margin **below par's** on the same seed, on seeds 1–3. A cast that changes nothing fails it.
- **Alt build expectations** live with the builds, in `altExpectations` ([maps.md §6.4](../design/maps.md#64-balance-harness)). A1M1's: `rivet_only` wins below par and at ≥ 40%, `par_minus_last` (par one purchase short) wins at ≥ 40%, and two under-built alts: `no_upgrades` (`outcome: 'either'`) and `two_rivets` (`outcome: 'lose'`). The validator rejects an expectation for a build the map doesn't have, an empty one, and an `outcome` combined with `minMarginPct` or `belowPar`.
- **No single-wave wall** (check `gradual`, every alt build, seeds 1–3; [maps.md §6.1](../design/maps.md#61-per-act-targets)): no wave of the run costs more than 50% of max integrity (or of a Protect map's asset meter, or of an Escort's `maxLost` refugees (the losses that lose it), booked to the wave of the unit that hushed or took each), and a run that loses has leaked (at the core or the asset) in an earlier wave than the one it loses in. Its summary lists the integrity lost per wave. The judge is `notGradual()` in `checks.ts`, and its numbers (`MAX_WAVE_LOSS_PCT`, `LEAK_LEAD_WAVES`) are in `rules.ts`.
- **A1M1's robustness test** (`src/balance/a1m1.test.ts`, part of `npm test`) re-runs the whole harness on A1M1 with W5–W7's clumps shifted ±0.1 and ±0.2 s apart (the three waves together), and expects every check to pass, so the tuning can't rest on a cliff. Every check includes the alt builds' `gradual` checks, so the under-built alts can't hit a wall under a shift either. It also checks that three setup Rivets and nothing else (a reference that isn't an alt build) lose no earlier than W6 and pass the same `notGradual()` judge, and that W7's strike is worth 4–6 integrity to par.
- **Assertion 14** runs par once per `flagVariants` value (run label `flag:<flag>=<value>`, seeds 1–3) with `scriptFlags` holding just that flag, and judges it like #1–2. On a map whose events revoke a tower class (A3M2's Clean Exit; T606, `src/balance/revokeChecks.ts`) it also runs par once per class of par's loadout the cue could take (run label `revoke:<tower>`, seeds 1–3, the cue forced onto it by `SimConfig.revokeClass`): each must win at the forgiving floor or better, and its cue must have taken that class. `HeadlessResult.revoked` lists what a run revoked; a step the executor skipped after a revocation is `skipped` in its record. It is checked on `FLAG_VARIANT_CONTENT` in `src/balance/__fixtures__/fireControl.ts` (a W3 grant under `spared_quiet_wave = true`) until a live map's script reads a flag. Per-value build overrides arrive with A3M5.
- **Assertion 16** (`freeChoiceChecks.ts`, seeds 1–3; (a) is live on A1M5, and both parts are checked on the fixture map in `src/balance/__fixtures__/fireControl.ts`): (a) on a map with a `quiet_wave` group, the run `holdFireWhile:quiet_wave` (par with the macro armed before W1, `withHoldFireWhile`) must win with its margin in band once the Quiet Wave's designed cost (`quietWaveCost`: each `quiet_wave` unit's leak, younglings' 0, as a share of max integrity) is given back, and its stats must make `spared_quiet_wave`'s own run-end rule true (Old Thrum and ≥ 75% of the younglings leaked; `FLAG_RULES` in `content/dialogue/flags.ts`, evaluated by `src/story/flags.ts` whatever map the rule names). (b) On a map with a `fleeing` group, the `spareFleeing` run's margin must be ≥ par's − `SPARE_FLEEING_SLACK_PCT` (5) on the same seed.
- **Run-end flags** (check `flags`, seeds 1–3; `runEndFlagChecks` in `freeChoiceChecks.ts`; T412): a map's builds list each run-end flag that its map sets (`runEndFlags`: every `FLAG_RULES` rule whose `onMapEnd` is a campaign map must be listed there, `[run-end-flags]` in validateBuilds) with the runs that must **set** it (`setBy`: each must win, and the flag's own rule must hold over its stats) and the runs that must **not** (`notSetBy`: the rule must not hold). Runs are `par`, `spareFleeing`, `holdFireWhile:<tag>` (par with the macro on that tag armed before W1), or `alt:<name>`. A1M5: `spared_quiet_wave` set by `holdFireWhile:quiet_wave`, not by par. A2M3 lists `held_fire_second_look` (≥ 50% of the fleeing units leaked and plain Hold Fire used): set by `holdFireWhile:fleeing` (Hold Fire on every fleeing group as it comes through), not by par or by `spareFleeing` (the Spare runners filter alone isn't Hold Fire). The summary prints the stats the rules read (each tag's leaked/spawned, Hold Fire uses).
- **R&D picks** (check `rnd`, seeds 1–3; `src/balance/rndChecks.ts`; D060, T228): par is also run with each R&D pick the map allows (`rndPicks` in `profile.ts`: an R&D item whose grants all tune an ability par casts here, Orbital Strike Mk II or a Companion Rapport, stocked by this map, not already in the reference profile), as `par@rnd:<upgrade id>` on the reference profile plus that pick. Each must win. A map that lists picks in its builds' `rndPickChanges` (for example `['orbital_strike_mk2']` on A1M3) also requires each to **change a par result**: on at least one seed, par with the pick ends with a different outcome, margin, or medal set than par without it. A listed pick the map doesn't allow fails with the allowed list. A1M2 allows both Mk II and Rapport, and neither changes a result there (act1.md § A1M2); A1M1 allows none (they're stocked after it).
- **Par earns its medals** (check `medals`, every seed; `src/balance/medals.ts`): when a map's builds list `parMedals` (for example `['challenge']`), the par build must earn each of them on every seed. A1M1's par earns its Teamwork medal. Medals themselves are the sim's ([architecture.md § Medals](architecture.md#medals)).
- **Build steps run cleanly** (checked on every run, beside 12 and 13): no step errors, and par and the sensible alt builds get every step in before the map ends (`mustIssueEveryStep` in `harness.ts`). Exempt from the second half: par on Story (`par@story`: an easier map can end before par's last buys; T333) and under-built alts (a player who stops short may lose before the plan's end).
- **Refused, not skipped:** a map that needs an assertion the harness can't make yet fails with a "refused" check that names the task it waits for. That covers the objectives a harness row still refuses (`HARNESS_GATES`). `HARNESS_GATES` in `src/balance/refusals.ts` names the task that lifts each map-feature refusal. A profile that `meta/modifiers.ts` refuses (an unknown item, too many protocols) or a config the sim refuses (a gated feature) fails each run that needs it, with the reason.

**Report.** Always printed: per map, a PASS/FAIL verdict, each assertion with its summary and every failing seed, then a leaks-per-wave table for the first seed of each build with its result, credits left, and medals (`V P C`, with `·` for each one not earned). `--report` also writes `reports/balance.json` (every run in full) and `reports/balance.md`: the assertion table; a runs table (build, seed, result, margin, ticks, credits left, late steps, medals, **link uptime**: each link's active ticks from `stats.linkTicks` as a share of the run, hash, CPU ms); and, for the first seed of each build, a **per-wave table** (spawned, killed, leaked, integrity lost, the bank as the build phase opened, credits unspent as the wave started, early-call bonus, late steps) and a **per-tower table** (tile, tier, built tick, shots, kills, **damage**, and **DPS**). Damage is the HP the tower's hits took (`ProjectileHit.damage`, summed by the run tracker; shield-absorbed damage and overkill don't count), and DPS is that damage over the tower's whole life, from its build to its sale or the end of the run, build phases included. Under the tower table: ability kills, ally kills (Bricks's post), link uptime, and the jams: "none", or the most towers Jammed at once, jam uptime (the share of tower-ticks Jammed), and the ticks over 25% (`balance/jamLimit.ts`, T702). Exit code 1 on any failure.

**Sim time.** The CLI plans every map's checks on its main thread (`planMap` in `src/balance/harness.ts`: the checks and the runs they need, each once), shares the runs out over a pool of `worker_threads` workers, one per core and one run per job (`tools/simPool.ts`, `tools/simWorker.ts`; each worker compiles the content once), then judges each map from its runs (`judgeMap`) and the campaign (`judgeCampaign`: assertion 3 and the verdicts), in campaign order. The output is the same at any `--jobs`, byte for byte but for the times. The pool keeps **map affinity** (`mapAffinity`): each worker starts a map, the later maps first, and takes that map's runs while it has any; then it starts the next map nobody has started, and once every map is started it joins the map with the most runs left. So a heavy map's runs spread over every free core, `--map <id>` included, and each worker runs few maps: with every worker on every map, the sim took ~10% more CPU (V8 kept re-optimizing for the next map; T778). At M8 content (18 maps, 762 runs; T778, 2026-11-12) the runs take ~160 s of CPU and the whole sim ~190 s of CPU with the workers' startup, the finale's 71 runs ~25 s of it; on four free cores that is ~40 s of wall, where the old map-per-worker queue took ~42 s and a finale 2.5 times heavier took 64 s against 50 s (a replay of both queues on the measured run times). The CLI prints each map's run count and time and the total on its last line; a map's time is the wall time of its planning, its runs (wherever they ran), and its judging, so the maps' times add up to more than the total. **Assertion 13 times each run on its thread's CPU clock** (`HarnessOptions.cpuNow`, which the CLI and its workers set to `tools/simClock.ts` `cpuClockMs`, `process.threadCpuUsage()`), so another agent's gate can't trip it; the slowest run today (the finale's par) takes about 0.75 s, and the map and campaign totals stay wall time. The report's runs table shows each run's CPU ms.

Optional **guards** catch known cheese: built-in policies such as `spamCheapest` (the cheapest loadout tower on every pad), listed under `guards` in `builds.ts` with an expectation (`lose`, or `maxMarginPct`).

Step semantics, implemented by the scripted-build executor in `src/sim/headless.ts`:

- Steps run **strictly in order**. A step becomes eligible when the build phase before its `wave` begins (`wave: 1` is the pre-game build phase; the phase before wave N opens when wave N − 1 finishes spawning). It's issued as a normal `Command` **the first tick it's affordable** at the price the sim will charge (`purchasePriceInto`: cost modifiers, a free first build, a Clearance Sale) and its tower is unlocked, and later steps wait behind it, so builds stay valid through small cost changes. Buying the moment the bank covers a step matters: the previous wave's bounties keep arriving during the countdown, and buying only at its end leaks ([D021](../decisions.md#d021--2026-11-09--t105b-waves-economy-and-the-end-of-a-map)). A step still waiting when its wave starts goes in as soon as it can, and the report counts it as **late**.
- The executor applies each command at once with `applyPending()` (identical to applying it at the start of the next tick), so the next step sees its effect. Wave 1 starts once the setup's affordable steps are in.
- An `ability` step waits for its moment, then for the slot to be ready (`abilityReady`: its tick and wave-count cooldowns): with no `when`, as soon as it's eligible; `waveStart`, the first tick after its wave starts; `{ afterSec }`, that long after its wave starts.
- An `upgrade`, `specialize`, `sell`, or `targeting` step with no tower on its tile, or a command the sim rejects, is recorded as a **step error** and the build continues (the harness fails on any). Every step kind has a command (`scriptInput` since T605).
- A `specialize` step on an unlocked tier-3 tower waits for its spec's cost, like an upgrade; on any other tower it's issued at once, and the sim's rejection (`specLocked`, `needsTier3`, …) is the step error. A `clear` step sends the salvage drone and completes once the tile is queued; a later `build` on that wreckage tile waits until the drone has cleared it. A `build` on wreckage that was never sent for is rejected (`notBuildable`).
- Step kinds map one-to-one onto commands: `build`, `upgrade`, `specialize`, `sell`, `targeting`, `holdFire` (by tile or `'all'`), `spareRunners` (by tile or `'all'`), `ability` (with an optional `when: 'waveStart' | { afterSec }`), `clear` (wreckage), `callWave`, `interact` (click a marker as soon as it's clickable; without the step, the marker's fallback trigger fires; see below), and `scriptInput` (presses a forced input as soon as it is requested). After a scripted revocation, steps for the revoked class are skipped and the build continues.
- **One macro step:** `holdFireWhile: <tag>` issues plain `holdFire 'all'` on when a unit of that tag spawns and off once every such unit the waves started so far send has spawned and none is left (dead or leaked), again for each later wave that sends some: the Quiet Wave holds once, `fleeing` holds for each runner group as it comes through. **Gerald's macro**, `holdFireWhile: 'neutral'`, holds while any neutral unit is on the field and releases the tick after the last one leaves (`NeutralExited`), again on every pass, so par can earn Return to Sender (only aimed shots count as hits, D072). The validator accepts it only on a map that spawns a neutral unit. It's what a player does by hand, so the run stays a plain command log. Reaching the step arms a watcher and completes the step at once, so later steps don't wait behind it. The watcher reacts like a player: on the tick after the first tagged spawn, and off the tick after the last tagged unit (by the started waves' group counts) is gone. A rejected toggle is recorded as the step's error. `BuildExecutor.release()` stops the macros (a hold they started is turned off): the app's autoplay calls it when another build takes over mid-run, so `autoplay('none')` during Gerald's pass leaves the towers firing (T335).
- **`interact: <marker>`** (T409) is armed like a macro: reaching it completes nothing and holds nothing behind it, and the `interact` command goes in before the first tick the marker is clickable (at once if it already is); that tick is the step's issued tick. If the marker is interacted with first (its fallback fired), the step records `notClickable`; if the map ends first, it was never issued. The validator accepts it only for a marker in the map's `clickables`.
- **`scriptInput: <id>`** (T605) is armed the same way: the `scriptInput` command goes in on the first tick that forced input is pending (`state.pendingInput`), and that tick is the step's issued tick. While any forced input is pending the executor issues nothing else (steps, macros, and wave calls wait, as the sim would reject them), except that a later `scriptInput` step for the pending input is armed ahead of its turn. The validator accepts it only for an id some `forceInput` action requests.
- `callEarly: true` calls each wave the moment its countdown starts, after issuing whatever steps of that phase are already affordable. The built-in `alwaysCallEarly` policy is the par build with `callEarly: true`.
- `flagVariants` lists the story-flag values to test: `{ door_choice: ['convoy', 'warren'] }`. Each value may override the build's steps and `technicianAbility` where a variant needs a different plan (A3M5 under `quill_choice = rewrite` equips Suppressing Fire, because System Reboot is locked there).
- **Profiles:** `src/balance/profile.ts` turns a profile into a run's modifiers, spec unlocks, and difficulty through `meta/modifiers.ts`'s `metaModifiers`, the same code the game uses on a save, so the harness tests the real progression math ([meta-runtime.md § Meta](meta-runtime.md#meta-srcmeta)). Each map's `referenceProfile` is its row of `REFERENCE_PROFILES` (`src/content/upgrades/reference.ts`, the rows of [campaign.md §4.9](../story/campaign.md#49-shop-stock-and-the-reference-profile), written through A2M6: A2M1 adds the Lookout, A2M2 the Sprinkler's specs, Seed Money 1 and the Zapcoil tune-up, A2M3 the Sprinkler's second tune-up, A2M4 the Zapcoil's specs and the Zapcoil's and Rivet's second tune-ups, A2M5 nothing (C2 Return empties the bank), A2M6 the gifted Prism and Reinforced Core 2); a test holds every registered map to its row and prices the rows not yet registered on the campaign's timeline. A row owning a tower still ahead of its task (`TOWERS_AHEAD_OF_TASK`) fails the par-purchasable check, so a row goes live only with its license on the shelf. There are four profiles: the map's `referenceProfile` on Standard (most runs), the same on Story (`par@story`), the same plus one R&D pick (`par@rnd:<id>`, `rndPickProfile`), and the **full-catalog profile** (`fullCatalogProfile`): every ranked shop and R&D upgrade at its top rank, the protocol slots filled with `FULL_CATALOG_PROTOCOLS` (Head Start, Emergency Bulkhead, Linked Up), and the reference profile's spec unlocks (Engineering buys options, not power). It leaves out any grant whose sim gate is still closed and lists it in assertion 6's summary. A run unlocks the profile's specs for its loadout's towers only. `HarnessOptions.catalog` swaps the live catalog for a fixture's in tests. The sim itself never imports `meta/` or `balance/`.
- **Policies** live in `src/balance/policies.ts` and need no authored steps: `none` (no steps), `spamCheapest` (generates a build step for every pad), both still pressing a forced input as par's `scriptInput` steps do (T605), `alwaysCallEarly` (above), and `spareFleeing` (the par build plus `spareRunners 'all'` on before W1). `withoutAbilityCasts` derives `parNoAbilities` for the abilities check.
- The content test validates builds ([architecture.md § Validation](architecture.md#validation)).
- The same builds drive the smoke tests (`__sd.autoplay('par')`), so one encoding serves both.

### Browser smoke tests (`npm run smoke`)

**Playwright** (`@playwright/test`) with headless Chromium against the **production build** (`npm run preview`, started by Playwright's `webServer`). That way the gate catches build-only breakage. Headless Chromium renders WebGL in software, which is slow but correct.

Why Playwright: it drives a real browser, captures console output and page errors, takes screenshots, and queries the DOM UI by role and text. It's also what agents know best. We don't use Vitest browser mode because it tests components, not the booted game.

**Speed budget.** The smoke step's share of the gate is in [Gate time](#gate-time). Smoke flows play in real time only for the steps a player performs; anything longer (playing out waves) uses `fastForward`.

**Timing-dependent steps pause the page's clock.** A step that must land while something on real time is still under way (a line still typing, a bark or a radio hold still up, a relabel still blinking) races a loaded machine: the gate's load can let it finish between two steps. Such a flow installs Playwright's clock before it loads the page (`page.clock.install()`, which keeps time running as usual), pauses it just ahead of now around the step (`page.clock.pauseAt(now + margin)`, widening the margin if the round trip outran it), and resumes it after (`page.clock.resume()`); `smoke/dialogue.spec.ts`'s `pauseClock` is the worked example. Time, timers, and frames all hold while it's paused, so assert on the DOM, not on canvas motion, inside the pause.

## Performance rules

Budgets: sim tick ≤ 1 ms with 300 enemies and 40 towers; frame ≤ 8 ms CPU at 60 fps on a mid-range laptop; boot ≤ 300 ms; initial JS ≤ 1 MB gzipped.

**In hot loops** (per entity, per tick in the sim; per sprite, per frame in render):

1. **No allocations.** No object or array literals, closures, spreads, destructuring into new objects, `map`/`filter`/`forEach`/`reduce`, string concatenation or template strings, or temporary vectors. Use indexed `for` loops, scalar `x`/`y` fields, and module-level scratch objects in render. (The sim gets scratch space from `TickContext`, because pure modules have no module-level state.)
2. **Pool everything that churns:** enemies, projectiles, zones, events per frame, views, particles, and floating text. Return items to the pool; don't `destroy()` and re-create. In render, hide pooled objects with `setVisible(false)`.
3. **Monomorphic shapes.** Initialize every field in the factory, never add or `delete` properties later, and don't mix types in one field.
4. **Resolve once.** Look up string ids at spawn or compile time, never in a hot loop. Use direct object references and precomputed per-tick values (`cooldownTicks`, `rangeSq`).
5. **Cheap math:** compare squared distances, use integer ticks, no trig where arithmetic will do.
6. **Bound the work:** targeting scans are O(towers × enemies), which is fine at our scale. Retarget only when the current target is lost or every N ticks, and add a spatial hash only if profiling demands it.
7. **Render:** one atlas page where possible (keep batches unbroken), no per-frame texture creation, `DynamicTexture.render()` only on change (except the lighting overlay), at most 512 live particles.
8. **DOM UI:** update signals only when values change, never write layout properties every frame, and never read layout (`getBoundingClientRect`) in the frame loop.
9. **Measure before optimizing** anything beyond these rules. Use `__sd.perf()` in the browser, and the per-run timings from `npm run sim`.
