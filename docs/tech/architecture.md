## 1. Stack

| Tool | Version (Nov 2026) | Role |
|---|---|---|
| **Node** | ≥ 22.6 (22 is the Claude Code cloud default; 24 also fine) | Dev tooling. `tools/*.ts` run through Node's type stripping: native from 22.18, and the npm scripts pass `--experimental-strip-types` so any Node 22 works. `npm run sim` and the docs check rely on it. |
| **TypeScript** | 7.0.x (`typescript`), strict | Language and type checking (`tsc` is the native Go compiler in 7.x) |
| **Vite** | 8.x | Dev server and production bundler |
| **Phaser** | **4.2.x** | Rendering, input, animation, cameras, filters (WebGL) |
| **Preact** + `@preact/signals` | 11.x / 2.x | DOM UI overlay (HUD, menus, dialogue) |
| **Vitest** | 5.x | Unit, sim, and content tests |
| **Playwright** (`@playwright/test`) | 1.x | Browser smoke tests and screenshots |
| **oxlint** + `oxlint-tsgolint` | 1.x / 7.x | Linting, including type-aware rules |
| **Prettier** | 3.x | Formatting |

Output is a **static site** (HTML + JS + CSS, with no backend), playable in a desktop browser. Input and layout are designed so that touch can be added later (D001 #8).

### Why Phaser 4, not Phaser 3

- **Phaser 4 is the current stable line.** 4.0.0 shipped on 2026-04-10. 4.1.0 and 4.2.0 followed, and 4.2.1 is npm `latest`. Phaser 3 is the legacy line. We have no v3 code to migrate, so there's no reason to start on the older line.
- **Its renderer suits our look.** The v4 WebGL renderer is faster, and its unified filter system gives us camera bloom and glow (`Phaser.Actions.AddEffectBloom`, internal and external filters) for the "glowing emissives against inky dark" style. It also has a tint **fill** mode for hit flashes.
- **It's well documented:** an official v3→v4 migration guide, the "Phaser 4 Rendering Concepts" guide, and updated API docs.
- **The risk is training data.** Most tutorials, and most of what agents remember, target Phaser 3. **Agents must check the v4 API before using anything they remember from v3.** Known traps:

| Phaser 3 habit | Phaser 4 reality |
|---|---|
| `this.make.graphics().generateTexture()` / `Create.GenerateTexture` for pixel art | `Create.GenerateTexture` and the built-in palettes are **removed**. We bake our own textures (`textures.addCanvas` plus frames). |
| `roundPixels` defaults to `true` | Defaults to **`false`**. We set `roundPixels: true` explicitly. |
| `setTintFill(color)` | Removed. Use `setTint(color)` plus `setTintMode(Phaser.TintModes.FILL)`. |
| `preFX` / `postFX` | Replaced by `filters` (internal and external lists). |
| `RenderTexture.draw()` draws immediately | `DynamicTexture`/`RenderTexture` buffer commands until you call **`.render()`**. |
| `Phaser.Geom.Point` | Removed. Use `Phaser.Math.Vector2`. |
| `Phaser.AUTO` with Canvas fallback | The Canvas renderer is deprecated, and filters need WebGL. We use **`Phaser.WEBGL`**. |
| `setPipeline('Light2D')` | `setLighting(true)` (we don't use Phaser lights; see [art-direction.md §7](../art/art-direction.md#7-vfx)). |

### Why TypeScript 7 plus oxlint (not typescript-eslint)

TypeScript 7.0 (July 2026) is the native compiler: same language, and roughly 10× faster type checks. It ships **no programmatic API yet**, so typescript-eslint can't run on it. oxlint's type-aware mode (`oxlint-tsgolint` v7, built on TS 7.0.2) covers almost all of typescript-eslint's type-aware rules and is much faster. Vite and Vitest only strip types and never call `tsc`, so they're unaffected.

**Fallback:** if a tool we need breaks on TS 7, pin `typescript@6.0` and switch to `typescript-eslint`. Record that as a decision.

## 2. The hard boundary: sim vs render

```
               ┌──────────────────────────── browser ────────────────────────────┐
               │                                                                 │
  input ─────▶ │  render/ (Phaser)      ui/ (Preact DOM)      story/   audio/     │
               │      │   ▲                 │    ▲              ▲         ▲       │
               │      │   │ read-only       │    │ view models  │ events  │ events│
               │      ▼   │ state           ▼    │              │         │       │
               │  ┌─────────────── app/ (host: loop, routing) ───────────────┐   │
               │  │   commands ──▶  sim.enqueue()     sim.step() × N         │   │
               │  │   events   ◀──  sim.drainEvents()                        │   │
               │  └──────────────────────────────────────────────────────────┘   │
               │                         sim/  (pure TS, deterministic)          │
               └─────────────────────────────────────────────────────────────────┘
```

**`src/sim/` is pure TypeScript.** It never imports Phaser, the DOM, `render/`, `ui/`, `audio/`, `meta/`, or `balance/`, and never uses `Date`, `Math.random`, `performance`, timers, or `localStorage`. This is enforced three ways:

1. **Separate tsconfig.** `tsconfig.pure.json` covers `src/sim`, `src/content`, `src/story`, `src/balance`, and `src/shared` with `"lib": ["ES2023"]` and `"types": []`. Any DOM global (`window`, `document`, `HTMLCanvasElement`) is a **type error** there.
2. **An architecture test** (`src/shared/architecture.test.ts`) scans the imports (static, re-export, dynamic `import()`, `require`) of every file in `src/` and fails on any edge the [allowed dependencies](#4-other-modules) forbid: pure modules may import no packages (only `vitest`, in tests) and only the modules they depend on; `render`, `ui`, and `audio` reach `sim` only through `sim/index.ts`. It also scans the code the sim executes, `src/sim/`, `src/shared/`, and `src/content/rules.ts` (comments and strings excluded), for the banned `Math` members below, any `Math` use other than `Math.<member>` (so aliasing can't hide a ban), and the globals `Date`, `performance`, `setTimeout`, `setInterval`, `requestAnimationFrame`, `localStorage`, and `globalThis`. This is the authoritative check.
3. **Lint** (`no-restricted-imports`, `no-restricted-properties`, and `no-restricted-globals` in `.oxlintrc.json`) gives fast editor feedback.

Rendering **reads** sim state and **sends commands**. It never mutates sim state.

### Determinism

- Same content + same map + same seed + same command list ⇒ the **same outcome**, on the same JS engine. That's what tests, balance sims, checkpoints, and reproducible bug reports need. Bit-exact results across browsers aren't a goal (there's no multiplayer or server replay).
- **Fixed timestep: 60 ticks per second.** `TICK_HZ = 60` (`src/shared/time.ts`, with the seconds → ticks conversions). Sim time is an integer `tick` counter. Content is authored in seconds and tiles, and converted to ticks once at content compile time.
- **Seeded RNG:** `sfc32` (128-bit state as four plain numbers, so it hashes and serializes) in `src/shared/rng.ts`. The sim derives one **stream per system** from the run's seed (`state.rng.waves`, `state.rng.towers`, …, each `forkRng(root, '<system>')`), so adding a random roll in one system doesn't shift every other system's results. `forkRng` reads its parent without advancing it, so adding a stream doesn't shift the others either. Use the integer helpers (`nextInt`, `nextIntBetween`, `chance`) rather than scaling floats yourself. Cosmetic randomness (particles, Hollow glitches, bark choice) uses separate render-side or story-side RNGs and **never** touches the sim's.
- Iteration order is always array order (entities are processed in ascending slot order). No `for…in` over objects, and no sorting without a deterministic tie-break.
- **Banned in `src/sim/`, `src/shared/`, and `src/content/rules.ts`** (everything the sim executes): `Math.sin`, `Math.cos`, `Math.atan2`, `Math.pow`, and `Math.random` (lint rule plus the architecture test). Their results can differ between engines, and none is needed: use squared distances, precomputed polyline lengths, and `x * x`. Lead targeting solves along the route's `dist`, not with angles.

### Entity model: typed pools, not an ECS

We have about 5 entity kinds and at most a few hundred live entities. A generic ECS would be more machinery than it's worth. **The simplest thing that works:**

- One **typed pool per kind**: `towers`, `enemies` (including neutral units such as Gerald, flagged `neutral`), `projectiles`, `zones` (ground effects, ability areas, and song auras), and `allies`. Each pool is a preallocated array of plain objects with every field initialized (monomorphic shapes), plus a free list.
- **Allies** are every friendly non-tower unit ([design/maps.md §5.4](../design/maps.md#54-allies-on-the-map)). Each has an `allyKind` (`swarmling`, `leaper`, `refugee`, `bearer`, `singer`, `bricks`, `militia`, `ward`), a movement mode (`route`, `post`, `owner`, or `stationary`), an optional attack (Bricks and militia), an optional song aura (singers, bearers), and a **vulnerability**: `never` (swarmlings, leapers, militia, wards, Pebble, Old Thrum), `hush` (refugees, singers, bearers), or `scripted` (Bricks in A3M3: Hollow units stop at his post, but his health bar follows a per-wave timeline in map data, never the player's DPS). Enemies never target towers.
- **Ally targeting.** Ally attacks never target units whose wave group is tagged `quiet_wave`, `youngling`, or `fleeing` (`WaveTag`, [§3 Data shapes](#data-shapes)).
- **Hushing:** a non-boss Hollow unit hushes at most one `fleeing` enemy or `hush` ally and turns Heavy. The fleeing and hush rules (tell, heal, speed, the Maw's gather) have one home, [design/enemies.md](../design/enemies.md) §5.4. In code, the victim is removed and the unit sets `hasHushed = true` so it can't hush again.
- Each entity has a `slot`, a `uid` (a monotonic integer from one run-wide counter, `state.nextUid`, never reused within a run; `0` marks a free slot), and an `alive` flag. Killing an entity (`poolKill`) clears `alive` but keeps the uid, so later systems in the same tick can still name it in events. `cleanup` returns dead slots to the free list at the end of the tick (`poolReleaseDead`), and `poolAlloc` resets every field from the kind's frozen blank when it reuses one. A full pool grows by one slot rather than failing. The pool code is `src/sim/pool.ts`; the entity shapes and blanks are `src/sim/entities.ts`, and each behavior task adds the fields it needs there.
- Entities hold a **direct reference to their compiled definition** (`def: CompiledEnemyDef`; towers also `tierDef`, the current tier), resolved at spawn, so hot loops never look up string ids. Entities refer to **each other only by uid** (`targetUid`, `towerUid`), never by object reference, so sim state has no cycles and `hash()` can walk it.
- Status effects ([design/enemies.md §2.4](../design/enemies.md#24-status-effects)) are **fixed fields** (`chillPct`, `chillMul`, `chillTicks`, `soakedTicks`, `corrodedStacks`, `corrodedTicks`, `markPct`, `markTicks`, `pinnedTicks`, `stasisTicks`, `stasisImmuneTicks`, `unnervedTicks`, `revealedTicks`, and on towers `jammedTicks` and `jamImmuneTicks`), not dynamic lists. Towers also carry `builtTick` and `firstFiredTick` for the misclick-grace refund ([design/core-loop.md §2.3](../design/core-loop.md#23-credits-the-in-map-currency)); for pulse and aura towers, `firstFiredTick` is the first pulse that affects an enemy. Each tower also has `holdFire` and `spareRunners` booleans (Hold Fire and the targeting filter, [§ Commands](#commands-input-into-the-sim)), `spec` (`'a'`, `'b'`, or null below tier 4), and `linkMask` (its active links, bit *i* = the *i*-th link in the compiled link registry). Entity fields are scalars or frozen content, never mutable objects or arrays: `poolAlloc` resets a slot with `Object.assign` from the frozen blank, which would share them.
- Enemies follow **predefined routes**. Map data gives ground paths and rift lanes as ordered tile sequences, and air lanes as polylines ([design/maps.md §4](../design/maps.md#4-paths-and-air-lanes)). Compile turns each into a polyline through tile centers with precomputed cumulative lengths. An enemy stores `dist` (tiles traveled) and `seg` (the segment `dist` lies on), and `x, y` are derived from those each tick (`src/sim/path.ts`: `placeOnRoute`, `pointAt`, `segmentAt`). A spawned enemy starts at its spawn tile's center (`dist` 0) and leaks on the tick it reaches the core tile's center. Movement adds `speedTilesPerTick × chillMul` to `dist` each tick, using only `+ − × ÷` on doubles (bit-identical on every engine), with a 1e-9-tile arrival tolerance so float sums don't land a tick late. `dist` also gives "first / last" targeting and lead targeting (predict `dist + speed × flightTicks`, then `pointAt`) for free.
- Systems are **plain functions** `(state: SimState, ctx: TickContext) => void`, run in a fixed order:

Win and lose conditions, economy, and every mechanic rule (damage pipeline, targeting tie-breaks, jam limits, beam armor per tick) are defined in [design/core-loop.md](../design/core-loop.md), [design/towers.md](../design/towers.md), and [design/enemies.md](../design/enemies.md). The sim implements them; it doesn't redefine them. The sim also records per-run **story stats** in `state.stats` for story and meta to read: `skitterkinKilled` (the run's Pests Processed: Skitterkin enemies killed by towers or abilities), `killsByEnemy`, `holdFireTicks` (ticks with any live tower holding), `holdFireUses` (`holdFire` commands that turned Hold Fire on where it was off), `ticksSinceFiredAtSkitterkin` (reset whenever a tower fires at a Skitterkin target or pulses one; frozen while no Skitterkin is in range of any attacking tower), and, per wave **tag**, `tagSpawned` / `tagLeaked` / `tagKilled` (kills by towers, abilities, and allies) ([design/core-loop.md §2.7](../design/core-loop.md#27-hold-fire)). It also tracks `medalExemptLeaks`, the meter (`evacuated`, `lost`, `voices`), and in the finale `restPoints`, `restTarget`, and `boreProgress`. All are integers.

**Combat** (`src/sim/combat/`, the `status`, `towers`, and `projectiles` systems) implements those rules. The details the design docs leave to code:

- **One damage entry point.** Every hit (tower shot, shell splash, pulse, and the Orbital Strike) goes through `applyDamage(state, enemy, amount, type, source, hit?)` in `combat/damage.ts`: the [enemies.md §2.3](../design/enemies.md#23-damage-pipeline) pipeline, then the kill. `source` is a `DamageSource` (`{ kind: 'tower', uid }`, `{ kind: 'ability', slot }`, or `{ kind: 'ally', uid }`); `hit` carries `armorPierce`, `ignoresArmor`, `isDoT`, and `beamTickSec`, and a `CompiledAttack` satisfies it. On-hit statuses apply after the hit's damage (`applyEffects`), so a Soak never boosts the hit that applies it. A kill (`killEnemy`) is the one place kills are booked: `skitterkinKilled`, `killsByEnemy`, the bounty, and `EnemyDied { killer, bounty, x, y }`, then `SackBurst { route, dist, young }` for a carrier (the Brood Hauler, `EnemyDef.carrier`): its young are render-only and never sim units.
- **HP is fractional** in the sim (the pipeline multiplies), and an enemy at or below `DEAD_HP_EPS` (1e-9) HP is dead, so float residue never costs an extra shot.
- **Targeting** (`combat/targeting.ts`) scans in ascending slot order on squared distances. A single-target tower picks by priority whenever it's ready to fire, and between shots keeps its target while it stays alive, hittable, and in range (so `targetUid` is always current for render). With no minimum range, distance 0 is in range (a flyer over the tower).
- **Timing.** A tower fires on a tick whose `cooldownTicks` starts at 0, then waits `cooldownTicks`. A new tower **deploys** first ([design/core-loop.md §2.5](../design/core-loop.md#25-building-upgrading-selling)): `build` sets its cooldown so its first shot or pulse comes exactly `TOWER_DEPLOY_SEC` (0.5 s, `content/rules.ts`) after the build tick. Upgrades don't reset the cooldown. Spin-up runs from acquiring a target after having none. A pulse tower waits at 0 until an enemy is in range, so its first pulse always affects one (misclick grace). A lobbed shell lands exactly `flightTicks` after the tick it fired, after that tick's movement, so a lead shot at a target holding its speed lands on its center. A Chilled of *N* ticks slows exactly *N* movement ticks.
- **Shells** copy everything the impact needs at fire time (damage, armor fields, splash, layers, effects), so selling or upgrading the tower mid-flight changes nothing. Splash hits only the layers the firing tier targets, and every victim is chosen before any damage lands.
- **Commander abilities** (`systems/abilities.ts`, [design/core-loop.md §3](../design/core-loop.md#3-commander-abilities)). Slot 1 holds `abilities.slot1`; slot 2 holds `abilities.slot2` only while `slot2State` is `present` (an `absent` companion's slot is shown dark and can't be used). `applyCommands` hands the `ability` command to `applyAbilityCommand`, which rejects `noAbility` (an empty or absent slot), `abilityOnCooldown`, or `invalidTarget` (a missing target, one off the map, or for a segment a tile no ground route crosses). An accepted cast opens its **zone** or zones (`abilitySlot` names the source), sets `state.abilityCooldownTicks[slot − 1]` to the modified cooldown, counts `stats.abilityUses`, and emits `AbilityUsed { slot, uid, ability, target }` (`uid` is the first zone's). Each tick the `abilities` system counts every cooldown down and runs the zones, all victims chosen before any damage, through `applyDamage` with `{ kind: 'ability', slot }`:
  - A **strike** (Orbital Strike) lands exactly `delayTicks` after the tick it was cast, before that tick's movement, on every **ground** enemy whose center is within its radius (inclusive, like splash; the strike isn't an air answer in `COUNTER_ANSWERS`).
  - A **segment** (Suppressing Fire) covers the clicked path tile ±`reachTiles` along **each ground route** whose tiles include it (one zone per route; air lanes never), shifted inward at a route's spawn or core so it keeps its length, and padded half a tile at each end so it covers those tiles whole: `distFrom ≤ dist ≤ distTo`. For `durationTicks` from the cast tick, every enemy on it is Chilled `slowPct` each tick (the strongest-chill rule, so it doesn't stack with a Sprinkler; it lingers one movement tick after the enemy leaves), and every 0.25 s it takes `damagePerSec × 0.25` as a **beam tick** (armor prorated, [enemies.md §2.3](../design/enemies.md#23-damage-pipeline)), the last on the zone's final tick: 20 ticks, 100 damage to an unarmored enemy that stays on it.
  - **Modifiers.** `abilityStats(def, modifiers)` applies `abilityStat` modifiers that name the ability (or `'*'`) by the stacking formula: cooldown (`flat` in seconds; at least one tick) and a strike's radius. Companion Rapport is cooldown −15% on its companion's ability, Ability Coolant −5% on every ability, and Orbital Strike Mk II radius +0.5 flat. The HUD reads the same function for the cooldown wipe and the reticle.
  - **The companion slot.** `companionSlot(content, map, picked?)` (`sim/companion.ts`) turns a map's `companion` into SimConfig's `companion`, `abilities.slot2` (the ability whose `companion` field names them) and `slot2State`; on a pick-list map the first is the default. `createSim` refuses a slot 2 without a companion, a companion without a slot, a `present` companion with an empty slot, an ability in slot 2 that isn't that companion's, and an `abilityStat` modifier that names an unknown ability or a radius on a segment.
  - Abilities are ready from tick 0. Cooldowns run on sim time, so an ability aimed while paused (`applyPending()`) lands as if cast on the next tick; an early call cuts them through `reduceAbilityCooldowns`.
- **Allies** (`systems/allies.ts`, system 7b). The map's ally **posts** (`MapDef.allies`: kind, a decor marker, a hitscan attack) spawn on tick 0, in map order, at their tiles' centers, in mode `post` with vulnerability `never` (`AllySpawned`). An ally fires like a hitscan tower (on a tick whose cooldown starts at 0, then waits `periodTicks`) at the **nearest** enemy in range (inclusive, ties to the lowest uid) on a layer it hits, re-picking every shot, and never a unit whose wave group is tagged `quiet_wave`, `youngling`, or `fleeing` (`allyMayTarget`). Its hits go through `applyDamage` with `{ kind: 'ally', uid }`, so bounties and kill counts book as for a tower, and each shot emits `AllyAttacked`. `removeAlly` (for scripts, M3) emits `AllyRemoved`. The headless tracker's invariants (#12) check that no ally attacks or targets an exempt unit, that never-vulnerable allies keep full health, and that allies stay on the map.

**Waves, economy, and the end of a map** (the `waves`, `triggers`, and `cleanup` systems, `applyCommands`, and `src/sim/economy.ts`) implement [design/core-loop.md §2.1–2.5 and §2.9](../design/core-loop.md#2-in-map-loop). The formulas and numbers are in `content/rules.ts` (`waveClearBonus`, `earlyCallBonus`, `SELL_REFUND_PCT`, `MISCLICK_GRACE_SEC`, the tagged bounties). The details the design leaves to code:

- **The schedule** is `state.schedule`: `phase` (`setup` → `spawning` ⇄ `countdown` → `done`), `waveTicks` (the spawning wave's clock), `countdownTicks` and `countdownTotalTicks` (0 outside a countdown), `countdownWave` (the highest wave whose build phase has begun: 1 in setup), and per wave `startTick`, `remaining` (enemies not yet dead or leaked, unspawned ones included), and `resolved`. Only one wave spawns at a time, because a wave can be called only during a countdown.
- **Spawning.** A wave's spawn clock starts at 0 on the tick it starts (a `callWave` applied by `applyPending()` starts it on the next tick). Group *g*'s *i*-th unit spawns at `delay + i × interval`, groups in parallel and in authored order within a tick, with full `hp` and `shieldHp`, at its route's start. On the last spawn tick the next wave's countdown starts (`CountdownStarted`), and its wave-phase `countdown` triggers fire that same tick. When it reaches 0 the wave starts (`WaveStarted { early: false }`).
- **`callWave`** in setup starts wave 1 for free. During a countdown it starts the next wave now, credits `earlyCallBonus(wave, countdownTicks, countdownTotalTicks)` (`WaveStarted { early: true, bonus }`), and cuts every ability cooldown by `round(0.25 × countdownTicks)` ticks. While a wave spawns it's rejected `waveInProgress`; after the last wave starts, `noWavesLeft`.
- **Bounties** are credited in `killEnemy` through `payBounty`: the enemy's `bounty`, 1 for a `fleeing` unit, 0 for a `youngling` (`bountyFor`), then the `bounty` modifiers' percentage. Credits are whole, so the fraction that percentage earns carries to the next kill (`state.economy.bountyCarry`). `EnemyDied.bounty` is what was paid. Leaks pay nothing.
- **Sell** refunds `sellValue(tower, state.tick, state.economy.sellRefundPct)`: everything invested while `firstFiredTick < 0` and fewer than 600 ticks have passed since `builtTick`, else `floor(invested × 0.7)` (Resale Value raises the 0.7; float slack makes 0.7 × 180 126). Sim time is ticks, so paused time never counts. The tile frees at once, so a sell and a rebuild can share a tick. Shells in flight still land.
- **Resolution, win, and loss** are `cleanup`'s, at the end of the tick: each enemy that died or leaked this tick decrements its wave's `remaining`. Then integrity 0 loses (`MapLost`, which beats a same-tick win). Otherwise every started wave at 0 resolves, in wave order within a tick (waves overlap, so they can resolve out of order across ticks), credits `waveClearBonus(wave)`, and emits `WaveCleared { wave, bonus }`. When every wave has resolved, the map is won (`MapWon`). Either way `outcome` is set, `step()` does nothing after, and commands are rejected `mapEnded`.
- **Script triggers** fire on the first tick they're reached, in map-event order (`state.scriptFired`). Every trigger the sim runs is monotonic, so `once: false` changes nothing yet. A `cleared` trigger fires on the tick after its wave resolves. An event's `when` is judged once, on that tick: if it doesn't hold, the event is spent without running its actions.
- **Stats.** `creditsSpent` is gross (builds and upgrades); `creditsRefunded` counts sells, so net spending is the difference. `creditsEarned` counts bounties, clear and early-call bonuses, and script grants.
- **For the HUD** (`sim/index.ts`): `state.schedule` for the countdown, `callWaveBonus(state, map)` for the call button's bonus (0 outside a countdown), `sellValue(tower, state.tick, state.economy.sellRefundPct)` for the sell button, `costFor(sim.config.modifiers, tower, base)` for build prices, `isLinkActive(state, content, id)` and each tower's `linkMask` for its links, and `towerStats(def, tier, tower, sim.config.modifiers)` (`sim/towerStats.ts`) for the tower panel's stat line under the tower's bonuses (with a link's `vsStatus` damage) and the next tier's delta and price, as simulated (rate from the whole-tick cooldown).

#### Medals

**Medals and conditions** (`src/sim/medals.ts`, `src/sim/conditions.ts`) implement [design/progression.md §3](../design/progression.md#3-medals-and-intel) and the medal-exempt rule ([design/core-loop.md §2.7](../design/core-loop.md#27-hold-fire)). The condition grammar is in [story-runtime.md § Conditions](story-runtime.md#conditions).

- **`state.medals`** holds `victory`, `perfectCore`, and `challenge`, each `open`, `forfeited` (it can't be earned this run), or `earned` (at victory). Every change emits `MedalProgress { medal, status }`, always before `MapWon` / `MapLost` on the tick that ends the map.
- **`cleanup` keeps them**, every tick: a dead enemy left at its route's end leaked (`leakedThisTick`); a medal-exempt one (a group tagged `quiet_wave`, `youngling`, `fleeing`, or `medal_exempt`; `MEDAL_EXEMPT_TAGS`) adds to `stats.medalExemptLeaks`, any other forfeits Perfect Core at once, even when its leak cost 0 or Emergency Bulkhead absorbed it. Then `trackConditions` latches `passedMarker` passes in `stats.markersPassed` while this tick's dead are still in their pools, and an open Challenge whose condition has **settled** false (`settledCondition`: a run atom broke) is forfeited. A loss forfeits every open medal. A win earns Victory and an open Perfect Core, and judges an open Challenge with `evaluateCondition` on the win tick (state atoms as they stand, run atoms over the run).
- **A map without a Challenge** (A1M1 until T125) leaves `challenge` open and never emits for it.
- **Save ids** are `victory`, `perfect_core`, and the map's `medals.challenge.id` (`medalId`, `mapMedalIds`). At run end `earnedMedalIds(state, map)` lists the earned ones in that order; meta records them and applies the checkpoint rule ([meta-runtime.md § Run end](meta-runtime.md#run-end)). The HUD and briefing read `state.medals` live, and `map.medals.challenge` for the Challenge's `name` and `description`.
- **`HeadlessResult.medals`** is the final `state.medals`; the balance report prints it per run and the `medals` check holds par to the map's `parMedals` ([conventions.md § Balance sims](conventions.md#balance-sims-npm-run-sim)).

If profiling ever shows object pools are too slow (unlikely below about 2,000 entities), convert a hot pool to struct-of-arrays (`Float32Array` columns) behind the same system functions.

### Commands (input into the sim)

Every player action is a **command**: a plain, serializable object in a discriminated union.

```ts
type Command =
  | { type: 'build';      tile: GridPos; tower: TowerId }
  | { type: 'upgrade';    towerUid: number }               // next tier
  | { type: 'specialize'; towerUid: number; spec: 'a' | 'b' }
  | { type: 'sell';       towerUid: number }
  | { type: 'targeting';  towerUid: number; mode: TargetPriority }
  | { type: 'holdFire';   target: number | 'all'; on: boolean }      // stop firing
  | { type: 'spareRunners'; target: number | 'all'; on: boolean }    // the targeting filter
  | { type: 'clear';      tile: GridPos }                  // send the salvage drone to a wreckage tile
  | { type: 'ability';    slot: 1 | 2; target?: GridPos }  // commander abilities
  | { type: 'callWave' }                                   // call the next wave early
  | { type: 'interact';   marker: MarkerId }               // click a clickable world object (the Peeker rock, A2M3)
  | { type: 'scriptInput'; id: string };                   // the forced single input (SEAL, "Who's there?")
```

- The code is the home of the union as built: [`src/sim/commands.ts`](../../src/sim/commands.ts) holds every command through M2 and `RejectReason`. The sketch above is the full target; `clear`, `interact`, and `scriptInput` arrive in M3. `applyCommands` dispatches `specialize` to `src/sim/specialize.ts` and `holdFire` / `spareRunners` to `src/sim/fireControl.ts`.
- The host calls `sim.enqueue(cmd)`, and the command applies at the **start of the next tick**, or immediately through `sim.applyPending()` (below). `enqueue` copies the command, so the caller may reuse its object.
- `holdFire` (a tower uid or `'all'`) stops the tower attacking; it's the plain Hold Fire that C1 uses. A holding tower drops its target, its cooldown keeps running (it can fire the tick it's released), and its links and bonuses are untouched. `'all'` sets `state.holdFireAll` and every live tower's flag, and towers built while it's on start holding; `'all'` off clears every tower's flag, per-tower holds included (the HUD button is a master switch). A uid that names no live tower is rejected `noSuchTower`.
- `spareRunners` is the **"Spare runners" targeting filter** (from A2M1; the rules are in [design/core-loop.md](../design/core-loop.md) §2.6–2.7). With a tower uid it is the per-tower toggle. `'all'` is the global HUD toggle (hotkey Alt+H): it sets `state.spareRunnersAll` and every tower's filter (off clears them all), and towers built while it's on start with it on. A tower with the filter on never *picks*, or keeps, a unit whose wave group has a tag in `SPARE_TAGS` (`fleeing`, `youngling`; `content/rules.ts`) as its primary target (`pickTarget` / `isStillTarget` in `combat/targeting.ts`), and a pulse tower waits until an unspared unit is in range. Splash and chain hits, and a pulse fired for another unit, still land on those units.
- `interact` is accepted only while the marker is clickable (a `setClickable` script action). It is the input half of the clickable-world-object trigger ([story-runtime.md § Map scripts](story-runtime.md#map-scripts-story-driven-sim-changes)).
- The sim validates every command (affordability, a buildable and empty tile, a tower in the loadout, unlocked and not revoked, an ability off cooldown and not revoked). While a forced input is pending, **every command except the matching `scriptInput` is rejected** (`reason: 'forcedInput'`). Invalid commands emit `CommandRejected { cmd, reason }` so the UI can explain.
- The **command log plus the seed reproduces a run exactly.** The sim appends every command it applies, accepted or rejected, to `state.commandLog` as `{ tick, cmd }`, where `tick` is the tick it applied at (a command applied by `applyPending()` after tick *T* logs *T + 1*, the same as one applied at the start of tick *T + 1*). Replaying means enqueuing each entry just before that tick runs. The game keeps the log in memory for checkpoints and so a bug report can include a replayable code (dev builds), and balance-sim builds are just scripted commands.
- **Optional bark buttons** ("Who's there?" in Act I) are not commands. They never change play, so they stay out of the sim and the command log; story handles them ([story-runtime.md § Barks](story-runtime.md#barks)).

### Events (output from the sim)

- During a tick, systems push typed events into `state.events`.
  - **Combat:** `EnemySpawned`, `EnemyDied`, `SackBurst` (a carrier's sack, `sim/carrier.ts`), `EnemyLeaked`, `ProjectileFired`, `ProjectileHit`, `TowerBuilt`, `TowerUpgraded`, `TowerSpecialized`, `TowerSold`, `TowerJammed`, `HoldFireChanged`, `SpareRunnersChanged`, `LinkFormed`, `LinkBroken`, `AllySpawned`, `AllyAttacked`, `AllyRemoved`, `MedalProgress`, `AbilityUsed`, `WaveStarted`, `WaveCleared`, `BossPhase`, `MapWon`, `MapLost`, `CommandRejected`, `CheckpointReached { wave }`.
  - **Story-facing:** `ScriptCue { cueId }`, `NotFiringAtSkitterkin` (once per run, when `ticksSinceFiredAtSkitterkin` reaches `NOT_FIRING_TICKS` (`NOT_FIRING_SEC`, 10 s, in `content/rules.ts`); `state.notFiringAnnounced` remembers it), `SkitterkinKilledAhead`, `Hushed { hollowUid, victim: 'enemy' | 'ally' }` (the Hollow unit turns Heavy), `RefugeeSaved`, `AllyHealthChanged`, `EnemyLaidToRest { uid, restValue }`, `EnemyScattered`, `EnemyReformed`, `BossEnded { how: 'driveOff' | 'retreat' | 'pivot' | 'layToRest' }`, `ObjectiveChanged`, `ObjectiveCompleted { id }`, `TowerClassUnlocked`, `TowerClassRevoked { tower, refund }`, `TowerClassRestored`, `AbilityRevoked`, `ClickableChanged { marker, on }`, `Interacted { marker, by: 'player' | 'fallback' }`, `ForcedInputRequested { id }`, `ForcedInputResolved { id }`, and `TimerProgress` (secondary timer, emitted on each whole percent).
- After each frame's ticks, the host calls `sim.drainEvents(out)`, which **appends** every event since the last drain to `out` (the caller clears `out`) and empties the sim's buffer. Events wait in the buffer until drained, so a headless runner that ignores them should still drain now and then. The host dispatches the events to subscribers (render views, UI signals, story, audio) through the **typed event bus** in `src/shared/bus.ts` (a tiny `on/off/emit` emitter keyed by event `type`).
- **Inside the sim, systems communicate through state, not events.** Events are output only, which keeps the tick order explicit. Payloads as built are in [`src/sim/events.ts`](../../src/sim/events.ts). `ProjectileFired` and `ProjectileHit` fire once per attack of every kind (`uid` 0 when no projectile entity exists: hitscan and pulses), so render and audio see every shot. `ProjectileFired` carries what render needs to draw the shot without looking up the tower (which may be sold or upgraded by then): `sprite` (the firing tier's projectile sprite, null for hitscan and pulses) and `flightTicks` (a shell's flight, else 0).
- Events are infrequent compared to per-entity work, so plain object events are fine. Per-entity, per-tick work must not allocate ([conventions.md § Performance](conventions.md#performance-rules)).

### Map scripts

Story moments that change play run **inside the sim** as map data (`MapDef.events`, evaluated by the `triggers` system), so headless runs, replays, and the balance harness see exactly what a player sees. The trigger and action unions, flags in the sim, forced input, revocation, clickable objects, and rest and scatter are specified in [story-runtime.md § Map scripts](story-runtime.md#map-scripts-story-driven-sim-changes).

### Game speed, pause, and the host loop

The sim doesn't know about speed. The host (`createHost(sim)` in `src/app/host.ts`) wraps one sim, and `BattleScene.update(time, delta)` calls its `frame(delta)` once per rendered frame:

```ts
const TICK_MS = 1000 / TICK_HZ;
const MAX_STEPS_PER_FRAME = 4;                   // per 1× of speed
const MAX_FRAME_DELTA_MS = 250;                  // a background tab or a debugger pause
const cap = MAX_STEPS_PER_FRAME * Math.max(speed, 1);
acc += Math.min(delta, MAX_FRAME_DELTA_MS) * speed;   // speed ∈ {0 (paused), 1, 2}
let steps = 0;
while (acc >= TICK_MS && steps < cap) {
  sim.step(); acc -= TICK_MS; steps++;
}
if (steps === cap) acc = 0;                      // drop backlog rather than spiral
if (speed === 0) sim.applyPending();             // build/upgrade/sell land while paused
events.length = 0; sim.drainEvents(events); dispatch(events);   // then the after-frame listeners
```

- **The host's API:** `sim`, `bus` (the drained events, by type), `speed` / `setSpeed(s)` (pausing empties the accumulator, so paused time never banks), `enqueue(cmd)`, `frame(deltaMs)` (returns the ticks stepped; non-finite or negative deltas count as 0), `fastForward(ticks)` (steps exactly `ticks` with no cap and regardless of speed, then dispatches once; `fastForward(0)` applies pending commands without advancing time), `onAfterFrame(listener)` (runs after every dispatch: the HUD's signal sync), and `simMsPerTick()` (a smoothed mean, for `__sd.perf()`). Its unit tests are `src/app/host.test.ts`.
- **One frame, in order:** the host steps and dispatches (views are created and released by the events), then BattleScene positions every view from sim state and redraws the hover, selection, range ring, and placement ghost ([§ Rendering](#rendering)).

- Speeds are 1× and 2×, with 3× an open design question ([design/core-loop.md §2.8](../design/core-loop.md#28-speed-and-pause)). The loop handles any integer speed; 2× is two ticks per 16.7 ms of accumulated time, not a bigger timestep. Pause sets speed to 0. Full-screen dialogue scenes pause; build-phase barks don't ([story/style-guide.md](../story/style-guide.md)).
- **`sim.applyPending()`** is a zero-time, command-only step: it runs `applyCommands` on the queue without advancing `tick` or any other system. Applying commands at the end of tick *T* is identical to applying them at the start of tick *T + 1* (`applyCommands` runs first), so the command log stays replayable without knowing whether the game was paused.
- Rendering shows the latest tick's state with no interpolation. (At 60 Hz ticks this is smooth enough for pixel art; interpolation can be added later if 120 Hz+ displays look juddery.)

### Checkpoints

"Retry from wave N" ([design/core-loop.md](../design/core-loop.md) §2.12) needs no state serialization. A **checkpoint** is `{ wave, tick, commandCount }`, recorded by the host when the sim emits `CheckpointReached` (every 5 waves from Act II, per `content/rules.ts`; the finale also emits it at the start of Phase 2 through a `checkpoint` script action). Retrying re-creates the sim from the same `SimConfig`, replays the first `commandCount` logged commands headlessly up to `tick`, then hands the sim back to the host. Replay at uncapped speed costs the same as a headless run (well under 2 s even for the finale). Checkpoints live in memory for the current run only. Using one marks the run result `usedCheckpoint` (which forfeits Perfect and Challenge medals) and records `resumedFromWave`, which the defeat payout uses ([meta-runtime.md § Run end](meta-runtime.md#run-end)).

### Sim public API

```ts
// src/sim/index.ts (implementation: sim.ts, config.ts, state.ts)
export function createSim<K extends IdSpace = LiveIds>(cfg: SimConfig<K>): Sim<K>;
interface SimConfig<K> {
  content: CompiledContent<K>; mapId: K['map']; seed: number;   // seed: an integer in [0, 2³²)
  loadout: K['tower'][];              // ≤ 4 distinct (hard rule); never contains a revoked class
  companion: CompanionId | null;      // resolved from MapDef.companion (a pick list is resolved before the map)
  modifiers: Modifier<K>[];           // from permanent upgrades, difficulty, veteran mods
  difficulty: DifficultyId;           // 'story' | 'standard'
  abilities: { slot1: K['ability'] | null; slot2: K['ability'] | null; slot2State: 'present' | 'absent' | 'none' };
  scriptFlags: ScriptFlags;           // story flags that map scripts read (story-runtime.md § Map scripts)
  specsUnlocked: K['tower'][];        // towers whose tier-4 pair is unlocked (one purchase, both specs)
}
interface Sim<K> {
  readonly state: DeepReadonly<SimState<K>>;   // the live object, same every tick
  readonly config: SimConfig<K>;
  readonly map: CompiledMapDef<K>;
  enqueue(cmd: Command<K>): void;     // copied; applies at the start of the next tick
  step(): void;                       // one 60 Hz tick; a no-op once the map is won or lost
  applyPending(): void;               // zero-time, command-only step (works while paused)
  drainEvents(out: SimEvent<K>[]): void;   // appends to out, empties the buffer
  hash(): string;                     // 16 hex digits over all state, for determinism checks
}
// src/sim/headless.ts (also exported from src/sim/index.ts)
export function runHeadless<K>(cfg: SimConfig<K>, build: CompiledBuild<K>, opts?: HeadlessOptions): HeadlessResult;
export function createBuildExecutor<K>(sim: Sim<K>, build: CompiledBuild<K>): BuildExecutor;   // beforeTick(), steps, waveCalls
```

- **Id typing.** `K` is the content's id space ([§3 Data shapes](#data-shapes)): the game uses the live registries, tests use `src/sim/__fixtures__/sim.ts` over the content fixture. It types only the API's edges (config, commands, events); inside, the sim runs on plain string ids.
- **`createSim` validates the config** and throws a `RangeError` listing every problem: an unknown map, tower, or ability, a bad seed, or a loadout over 4 or with duplicates. It also checks `abilities.slot2` and `specsUnlocked` name real content. Until their tasks land it refuses what it can't simulate, rather than ignoring it, per feature: `FEATURE_GATES` in [`src/sim/gates.ts`](../../src/sim/gates.ts) maps each feature (a companion, slot 2, `specsUnlocked`, Story difficulty, each modifier kind, with `economy` split by stat, and each attack kind or on-hit status the `towers` system doesn't run yet: `projectile`, `beam`, `chain`, and `spawner` attacks and the Pinned, Stasis, and Unnerved statuses on any tier a loadout tower can reach, its specs included once unlocked) to the task that lifts it, and that task sets its own row to `null`. Map-script triggers and actions the `triggers` system doesn't run yet, and optional objectives (M3), are refused separately (`unsupportedScript` in `systems/triggers.ts`).
- **`state`** ([`src/sim/state.ts`](../../src/sim/state.ts)) holds everything that changes: `tick` (ticks completed; during a step, the tick being run, starting at 0), `nextUid`, `outcome`, `credits`, `integrity`, `maxIntegrity` (the run's starting integrity after modifiers, which Results shows the meter against), `wave`, `schedule` (the wave schedule; see *Waves, economy, and the end of a map* above), `scriptFired`, `lockedTowers`, `towerAtTile`, the five pools, the RNG streams, `stats`, `abilityCooldownTicks`, `holdFireAll` and `spareRunnersAll` (the global toggles new towers inherit), `notFiringAnnounced`, `linksDirty`, `linkPairs` (the active link pairs as `[link, uidA, uidB]` triples, which the links system diffs for its events), `leakAbsorbLeft` (Emergency Bulkhead), `economy` (the run's bounty, early-call, and sell-refund percentages after modifiers, plus the bounty carry), `medals` (each medal `open`, `forfeited`, or `earned`), the `pending` queue, and the output buffers `commandLog` and `events`. Immutable inputs (content, map, config) and per-tick scratch live in the `TickContext` that systems receive, not in state.
- **`hash()`** walks all of `state` generically except the output buffers, so a field added later is covered automatically. Numbers hash by their exact bits; a frozen object with a string `id` (a compiled definition or route) hashes as its id, so two runs over separately compiled but identical content agree. Two lanes (FNV-1a plus a second mix, `src/shared/hash.ts`) give a 64-bit digest. It isn't for hot loops.
- **`runHeadless`** runs one map to the end (or `maxTicks`, default 30 minutes of sim time) with no frame cap, issuing the build's steps through the scripted-build executor ([conventions.md § Balance sims](conventions.md#balance-sims-npm-run-sim)). It takes a ready `SimConfig` and a compiled build (`map.builds.*`, or a policy's); it never imports `meta/`. Its `HeadlessResult` holds the outcome, final integrity and credits, `hash()`, the wave a loss happened in, per-wave tallies (spawned, killed, leaked, integrity lost, the bank as the build phase opened, credits unspent at the wave's start, early-call bonus), per-tower shots and kills, each step's issue tick, lateness and error, and any invariant violations (`headlessTracker.ts` checks them after every tick).
- **`createBuildExecutor`** is the executor on its own: call `beforeTick()` before each `sim.step()`, and it issues whatever steps are due through `enqueue` + `applyPending()`. It never drains events, so a host can drive it alongside rendering: `__sd.autoplay(name)` (`app/autoplay.ts`) runs it from `host.setDriver`, which calls it before every tick of a frame or a `fastForward`.
- **The sim knows nothing about meta progression.** Permanent upgrades, Field Protocols, and difficulty arrive as a list of `Modifier`s. In the game, `app/` gets them from `meta/`. In the harness, `src/balance/profile.ts` composes a map's `referenceProfile` into modifiers through the same pure `meta/modifiers.ts` functions the game uses. For M1, A1M1's profile is empty, so its modifier list is empty.

**Modifiers follow the design's stacking formula** ([design/towers.md §4](../design/towers.md#4-stat-modifiers-and-stacking)): `stat_final = (stat_tier + Σ flat) × (1 + Σ pct)`, with percentages **added, never multiplied**, and per-stat caps on the total percentage.

The union as built, with each kind's documentation and the progression item it serves, is in [`src/sim/config.ts`](../../src/sim/config.ts):

| Kind | Changes | Progression sources (design/progression.md) |
|---|---|---|
| `towerStat` | A tower's (or every tower's) damage, rate, or range | Tune-ups ranks 1 and 3, the Zibzab Tune-up |
| `towerCost` | Build and upgrade costs (`tiers: 'all'`) or tier 4 only (`'spec'`) | Tune-up rank 2, Specialist |
| `enemyStat` | Enemy HP, shields, or speed | Story difficulty, veteran modifiers |
| `economy` | `startCredits`, `coreIntegrity`, `bounty`, `earlyCallBonus`, `salvage`, `clearSpeed`; `set` replaces the map's value first (lowest wins) | Seed Money, Reinforced Core, Bounty Hunter, Salvage Rights, Head Start, Salvage Expert, Early Bird, Bounty Board, Story (`coreIntegrity` set 30) |
| `sellRefund` | Adds to the sell refund fraction (0.7 → 0.75 → 0.8) | Resale Value |
| `abilityStat` | An ability's (or every ability's) cooldown or radius, by ability id | Ability Coolant, Orbital Strike Mk II, Companion Rapport |
| `countdown` | Wave countdown length | Story difficulty, veteran Rush Hour |
| `linkBonus` | Every link's bonus × (1 + pct) | Linked Up |
| `tileBonus` | Adds to a tile's bonus fraction (high ground 0.25 → 0.40) | High Ground Training |
| `leakAbsorb` | Absorbs the first *n* integrity lost to leaks, once per map | Emergency Bulkhead |
| `firstBuildFree` | The first tower each map costs nothing (tier 1) | Rapid Deploy |
| `freeCast` | Each ability's first cast in a given wave starts no cooldown | Ready Room |

`pct` is a fraction (+10% → 0.10). Every kind carries a `source` (`'shop:<id>'`, `'difficulty:story'`, …) for the UI's breakdown.

- **Tower stats** (`towerStat` modifiers and every in-map source) are summed into per-tower scalar slots (`flatDamage`, `flatRate`, `flatRange`, `pctDamage`, `pctRate`, `pctRange`, plus `vsStatusMask` / `vsStatusPct` for a link's conditional damage bonus) by the `links` system, recomputed only when something changes: a tower is built, upgraded, specialized, sold, or jammed, a jam expires, or (later) the lighting changes; never per tick. The sources: static `towerStat` modifiers for that tower or `'*'`; its tile (high ground +25% range, a power node +20% fire rate or, for a support tower with no attack, +20% aura strength; `tileBonus` adds to those fractions); each active link once (`linkBonus` scales every link's flat and percent); and auras, the strongest per aura kind, never the tower's own. The slots don't depend on tier, so an upgrade takes effect at once.
- **The final stat** is `(stat_tier + Σ flat) × (1 + min(Σ pct, cap))`, computed where it's read by the pure functions in `sim/bonuses.ts` (a few multiplies): the towers system for damage, range (a scratch `RangeSpec` for targeting), and the period (the simulated rate `60 / cooldownTicks` takes the bonuses and rounds back to whole ticks, so +10% on a 30-tick Rivet fires every 27), and `towerStats()` for the HUD (tiers 1–3, or tier 4 given the spec). A `vsStatus` bonus joins the damage percent, under the same cap, against an enemy with one of its statuses: checked per hit for hitscan and pulses, and per victim on impact for shells (a shell carries `damage` and `damageVs`, and Cluster Thumper's its bomblets' pair). Caps, aura kinds, tile fractions, and the status bit order are data in `content/rules.ts`, not hard-coded.
- **Costs and the run economy.** `towerCost` applies at purchase (`costFor`: `round(base × (1 + Σ pct))`; `'spec'` modifiers only on tier 4), and `invested` records what was paid. `createSim` applies the rest once (`applyRunModifiers` in `sim/economy.ts`): `startCredits` and `coreIntegrity` as `(set ?? base + Σ flat) × (1 + Σ pct)`, rounded (lowest `set` wins; integrity at least 1, and `state.maxIntegrity` records it); `leakAbsorb` into `state.leakAbsorbLeft`, which `movement` spends before the core loses any (`EnemyLeaked.leak` is what the core lost); and the `bounty`, `earlyCallBonus`, and `sellRefund` numbers into `state.economy`, so the HUD's helpers read the run's numbers. `bounty` and `earlyCallBonus` take `pct` only; a `set` or `flat` on them makes `createSim` throw.
- **Darkness** that affects play (A2M6 Sundown onward) is sim state set by the `setLighting` script action: a range penalty on towers outside every light source. A tower def's `lightRadiusTiles` (Prism Spire's beam) makes a light source, so nearby towers keep full range. Render draws the same sources as light stamps ([art-direction.md §7](../art/art-direction.md#7-vfx)).

## 3. Content (`src/content/`)

**Content is data**: typed TypeScript files, one entity per file, with explicit registries (no `import.meta.glob`, so the same files load in Vite, Vitest, and plain Node).

| Folder | Holds |
|---|---|
| `towers/` | Tower definitions: cost, tiers 1–3, two tier-4 specializations, attack behavior, sprite ids |
| `enemies/` | Enemy definitions: HP, speed, bounty, abilities, tell ids, sprite ids |
| `abilities/` | Commander ability definitions (Orbital Strike, Suppressing Fire, companion abilities) |
| `links/` | Synergy links ([design/towers.md §6](../design/towers.md#6-synergy-links-adjacency)): two partner towers, each with its stat bonuses (`flat`, `pct`, or a conditional `vsStatus` damage pct). The one home of who links with whom: compile lists each tower's links on its compiled def, and registry order is each link's bit in `Tower.linkMask` (at most 31) |
| `maps/<id>/` | One folder per map: `map.ts` (tiles, paths, air and rift lanes, markers, objective, credits, events, environment palette), `waves.ts`, `builds.ts` (`referenceProfile`, `parBuild`, `noCounterBuilds`, `altBuilds`, `altExpectations`, variants, guards), and `index.ts` composing them into one `MapDef` |
| `upgrades/` | Permanent upgrades (shop and R&D) as modifiers, each with `availableAfter` |
| `dialogue/` | `flags.ts`, `speakers.ts`, `scenes/<act>/`, `barks/<trigger>.ts`, `memos/` (Everglow Inbox), `epilogue/`, `tips.ts`, `results.ts`, `bricks_tags.ts` ([story-runtime.md](story-runtime.md)) |
| `codex/` | Codex entries, each with `original` / `annotated` / `corrected` versions and their unlock conditions |
| `presentation.ts` | The per-act presentation dials ([design/core-loop.md §6.7](../design/core-loop.md#67-per-act-presentation-dials)), with per-map overrides in map data |
| `campaign.ts` | Campaign map order (mirrors [story/campaign.md](../story/campaign.md)) |
| `rules.ts` | Rule data: damage matrix, status caps and the speed rule, stacking caps, aura kinds, jam limits, counter categories, the trait → counter-category and trait → tell maps (human-readable table: [design/enemies.md](../design/enemies.md) §3.1; intel-only traits map to `null`), which towers and abilities answer each category, threat-budget factors, map design limits, default countdowns and integrity, sell refund and misclick grace, tile bonuses, link adjacency and the status bit order for `vsStatus`, `SPARE_TAGS`, checkpoint interval. Bark thresholds join it with the story runtime |
| `sprites/`, `palettes/` | Pixel art data ([art/tech-spec.md §2](../art/tech-spec.md#2-code-generated-pixel-art-format)) |
| `types.ts`, `compiled.ts`, `define.ts` | Definition types (authored and compiled; [§ Data shapes](#data-shapes)) plus `defineTower()`, `defineEnemy()`, `defineMap()`, and similar identity helpers that give type inference |
| `registry.ts` | Imports every registry and exports `RAW_CONTENT` |
| `validate.ts` | Design-rule validation (below; its parts: `validateMap.ts` with `validateWaves.ts`, `validateThreats.ts`, and `validateScripts.ts`, plus `validateBuilds.ts` and `validateHelpers.ts`) |
| `compile.ts` | `compileContent()`: resolves ids to references, converts seconds to ticks, resolves tier patches, compiles routes and `towerUnlockWave`, and freezes the result into `CompiledContent` (its parts: `compileTower.ts`, `compileLinks.ts`, `compileMap.ts`, `compileBuilds.ts`, `compileHelpers.ts`) |

- **Ids** are `snake_case` strings, unique per kind. Id union types are derived from the registries (`type TowerId = keyof typeof TOWERS`), so a typo in a wave file is a compile error.
- **Exact numbers live in content files.** Design docs hold intent, roles, and target ranges, and link to the content file rather than copying its numbers.
- TS types check shape at compile time; `validate()` checks what types can't (cross-references, ranges, grid geometry, design rules). No schema library is needed, because content is TS, not JSON. Untrusted input (save import) gets its own validator in `meta/`.

### Data shapes

**The code is the home of the data shapes:** [`src/content/types.ts`](../../src/content/types.ts) defines what content authors write (`TowerDef`, `EnemyDef`, `AbilityDef`, `MapDef` and its parts, waves, builds, conditions, and the map-script triggers and actions), and [`src/content/compiled.ts`](../../src/content/compiled.ts) defines what the sim reads (`CompiledContent`). Design docs link there instead of keeping their own sketches. The essentials:

- **Units are in field names** ([conventions.md § TypeScript style](conventions.md#typescript-style)). Content is authored in seconds and tiles (`ratePerSec`, `rangeTiles`, `flightSec`); compiled data is in ticks and tiles (`cooldownTicks`, `rangeSq`, `speedTilesPerTick`). The tile is the sim's only distance unit; tile `(c, r)` has its center at `(c + 0.5, r + 0.5)` ([art/tech-spec.md § Grid ↔ screen math](../art/tech-spec.md#grid--screen-math)).
- **Id unions come from the registries** (`type TowerId = Extract<keyof typeof TOWERS, string>`). Types that refer to another kind's ids take an id space `K` that defaults to the live registries, so test fixtures (`src/content/__fixtures__/`) get the same typo checking against their own registries. A definition never names its own kind's ids (`MapDef.revisitOf` is a plain string that `validate()` checks), which keeps the types free of cycles. Kinds without a registry yet (upgrades, protocols) are `never`, so nothing can reference them until their task adds one.
- **Towers:** tier 1 is complete; tiers 2 and 3 are patches on the tier before, and the tier-4 specs (optional; a tower without them rejects `specialize` with `noSpecs`) patch tier 3. Targets and default priority live on the tier, so a spec can change them (Railspike's Strong, Cloudburst's air). Attack kinds: `hitscan`, `projectile`, `lobbed` (fixed flight time, optional lead, optional `bomblets` scattered on impact: Cluster Thumper), `beam`, `chain`, `spawner`, and `pulse` (hits every enemy in range each period, with no target: the Sprinkler's chill aura). Armor pierce and ignore-armor are attack fields on every kind.
- **Waves:** a group's `intervalSec` defaults to the enemy's `spawnIntervalSec` ([design/enemies.md §5](../design/enemies.md#5-roster)), and its `route` (a path, air-lane, or rift-lane id) also fixes its spawn. A wave's `countdownSec` defaults by act ([design/core-loop.md §2.1](../design/core-loop.md#21-phases)). Wave tags (`WaveTag`) include `quiet_wave`, `youngling`, and `fleeing`, which allies and the spare-runners filter never pick.
- **A map** is `MapLayoutDef` (`map.ts`) + `WaveDef[]` (`waves.ts`) + `BuildsDef` (`builds.ts`), composed by `defineMap` ([conventions.md § Add a map](conventions.md#add-a-map)).

**Compiling** (`compileContent()` in `src/content/compile.ts`; its header comment is the home of the conversion and merge rules) turns seconds into whole ticks and rates into whole-tick periods, resolves tier patches into full per-tier definitions, gives wave groups direct references to their compiled enemy and route, turns routes into polylines through tile centers with cumulative lengths, compiles `towerUnlockWave` into `{ wave: N, phase: 'countdown' }` → `unlockTowerClass` events (ahead of the authored events) plus the map's `lockedTowersAtStart`, turns build steps into tagged steps, resolves every optional field to a value or `null`, and deep-freezes the result. Anything it can't compile past (an unknown id, a registry key that differs from its id, a malformed tile grid, a route that breaks the route format) is reported with the validation errors in one `ContentCompileError`.

### Validation

`compileContent()` runs `validate()` ([`src/content/validate.ts`](../../src/content/validate.ts)) first and throws one `ContentCompileError` listing every validation and compile problem, so invalid content never compiles; each validation error reads `[rule] where: message`. **The code is the home of the check list:** the headers of `validate.ts`, `validateMap.ts`, and `validateBuilds.ts` name every rule they check, and `validate.test.ts` has one failing fixture per rule. `content.test.ts` validates the live registries (the schema test). The design rules are owned by the linked design docs; their values (caps, the trait → counter-category map, the answer lists, limits) live in `rules.ts`. In summary:

- **References and ranges:** ids exist (compile), sprites are registered and of the right category, numbers are in range on every resolved tier, enemy traits agree with the data and show their tells, and only the listed jammers jam. Sprite grids, master-palette colors, the Hollow hue reservation, and path-vs-pad contrast run through `sprites/validate.ts` and `palettes/validate.ts`.
- **Geometry** ([design/maps.md §9](../design/maps.md#9-map-data-shape-for-implementers)): the route format is a compile error (`compileMap.ts`), and so is an ally post naming an unknown marker. `validate()` adds: every wave group can walk its route, a Defend map has one core, markers (so ally posts) sit on decor, wreckage says what lies under it and pays 30–80 salvage, and `cols + rows ≤ 36` for campaign maps.
- **Threats** ([design/maps.md §6.2–6.3](../design/maps.md#63-one-new-thing-per-map)): `threatIntel` equals the traits in the waves; `requiredCounters` has at most 3 entries, each with a `noCounterBuilds` entry; soft enemies stay within 15% of every wave's threat; teach waves teach a new trait; in campaign order, at most two new threats and one new required-counter category per map.
- **Companions and allies:** each companion a map names `present` (or in its pick list) has an ability whose `companion` field names them, a companion has at most one ability, and a pick list is non-empty with no repeats; ally posts have sane attack numbers, one ally per post, and Bricks at most once.
- **Builds:** loadouts (≤ 4, owned by the reference profile; a build names a companion only from its map's pick list), what each scripted step means on the map (buildable empty tiles, unlocked towers, towers built by then, tiers and specs, a slot-2 cast only with a present companion or a pick), no-counter builds carry no answer to their category and alt builds carry one to every required counter (`content/counterAnswers.ts`: the tiers and specs a build's towers reach and the abilities it casts, [design/enemies.md §3.1](../design/enemies.md#31-counter-categories)), and from A1M4 there are at least 2 alt builds sharing at most 2 tower types with par.
- **Medals and conditions** (`validateMedals.ts`): every campaign map has a Challenge with a snake_case id that isn't built in, a name and description that fit the briefing, and a condition that never references medal-exempt units; every condition has sane bounds, and a `passedMarker` marker sits within 1.5 tiles of a route its units walk.
- **Scripts:** wave triggers, markers, objectives, and forced inputs exist; cue ids follow `<map_id>_wNN` or `<map_id>_<slot>` ([story/style-guide.md](../story/style-guide.md)); every flag a script reads has a `flagVariants` entry.
- **Feature guards:** content that needs a system that doesn't exist yet is refused rather than mis-simulated: bosses (M3, with the boss-leak rule) and non-Defend objectives (T305, with Escort safe exits).
- **Not yet checked** (TODO stubs in the code, waiting for content that can't exist yet): par is purchasable (T204), revisit layouts and locked abilities per flag variant (M5). The dialogue rules are in [story-runtime.md § Validation](story-runtime.md#validation).

### Rendering

Lives in `src/render/`.

- **Phaser config:** `type: Phaser.WEBGL`, `width: 640`, `height: 360`, `pixelArt: true`, `roundPixels: true`, `antialias: false`, `backgroundColor: '#05030a'`, `scale.mode: NONE`. `render/scale.ts` computes the integer zoom on resize (formula in [art/tech-spec.md § Tile and screen](../art/tech-spec.md#tile-and-screen)) and applies it to the canvas and to the UI root (`--ui-scale`, [§ UI: DOM overlay](#ui-dom-overlay)).
- **Scenes:** `BootScene` (bake sprites; later load fonts), `BattleScene` (the playfield), `StarMapScene` (M3), `BackdropScene` (the animated backdrop behind DOM menus: the night sky over Dome Row from the pure `vfx/backdropPixels.ts`, seeded so it's the same every boot, with twinkling stars and rising `stardust.sung` motes; still under reduced motion). `BootScene` and `BackdropScene` are in the game config; only `BootScene` starts on its own.
- **Screens and run end** (`src/app/router.ts`): `goto` shows a menu over the backdrop (`title`, `campaign` (the Shift board, which needs a loaded save), `base` (once the save has opened it), `loadout` (T201: it needs a loaded save and a campaign map; `app/loadout.ts` builds its view), or `settings`, whose Back returns to the menu it came from), `battle` (stops the backdrop and starts a session), or `results`. `play(request)` is the Shift board's Start. It shows the loadout screen when the save has a choice to make (`meta/loadout.ts`, the skip rule), else the battle and its briefing. A briefing after the loadout screen offers Change loadout (`loadoutChangeable`), and Lock in writes the pick as the map's preset before the battle opens. Going to `title` leaves the save in play. The router subscribes to the battle's `MapWon` and `MapLost` (and counts `WaveCleared`, and notes the first `EnemyLeaked`). When the map ends it freezes the battle (speed 0, selection cleared; game hotkeys go off with the sim's outcome) and waits `RESULTS_DELAY_MS` (1.5 s of real time, D028) so the last radio line and the leak's feedback play out; then at run end (`endRun`, once per battle; `flushResults()` skips the rest of the wait) it builds a `RunResult` (`app/runResult.ts`: waves survived, integrity left, `stats.skitterkinKilled` as Pests Processed, and the `debrief`: the map's `mapWon` or `mapLost` radio lines, led by its `firstLeak` line when the first leak came within 4 s of real time and 4 s of 2× game time of the end), applies the run end to the save in play (`app/save.ts` `recordRun` → `meta/runEnd.ts`: rewards, medals → Intel, the lifetime Pests Processed; [meta-runtime.md § Run end](meta-runtime.md#run-end)), and shows Results over the frozen playfield (`recordRun` also returns whether the slot write held, which Results shows as `saveNotice`, and a `stardustNote` while Stardust can't be spent yet). `retry()` replays the last battle request. A battle fails safe: its `battleConfig` is built before the menu is torn down, so a config that throws (a save the sim refuses) leaves the menu up with `menuNotice` (`ui/screens/state.ts`) set; a battle that fails to start returns to the Shift board with the same notice. A battle the request doesn't seed uses the URL's `?seed=` (else a random one), and one it doesn't name uses `?map=` (else `DEFAULT_MAP_ID`). The UI's buttons reach the router only through `app/navigation.ts` (`startGame`, `newGame`, `continueGame`, `loadGame`, `importGame`, `playMap`, `lockInLoadout`, `changeLoadout`, `toCampaign`, `toBase`, `afterWin`, `openSettings`, `closeSettings`, `retryRun`, `toTitle`), the screen counterpart of `commands.ts`.
- **The save session** (`src/app/save.ts`; the save API it uses is [meta-runtime.md § Save system](meta-runtime.md#save-system)): which campaign is in play and its slot, over a localStorage `KeyValueStore` (`browserKeyValueStore`: reads never throw, a refused write comes back as a cheerful "Records couldn't file that" message). It writes the menus' view models (`ui/screens/state.ts`: `slots`, the three slots' summaries; `campaign`, the save in play's slot, banks, difficulty, Shift board, and which base systems are open) after every change. Boot calls `initSaves(browserKeyValueStore())`; `?test=1&save=<id>` (and only with `?test=1`) loads a dev save into an in-memory scratch slot that never touches localStorage, with its `devUnlocks`, and boots onto its Shift board ([meta-runtime.md § Progress and gating](meta-runtime.md#progress-and-gating)). Every save it takes into play (opened, imported, or a dev save) first gets the towers the campaign has issued it by then ([meta-runtime.md § Issued towers](meta-runtime.md#issued-towers)).
- **Battles** (`src/app/`): `battle.ts` starts a session: one sim, its host, a `BattleInteraction`, and a `BattleScene` added under a fresh key (`Battle.<n>`), and stops it by removing the scene. `battleSetup.ts` turns a map id and the save in play into a `SimConfig`: the loadout from `meta/loadout.ts` `resolveLoadout` (the map's preset from the loadout screen while the save has a choice; otherwise `defaultPick`: the save's unrevoked towers, all of them up to four, par towers first above four, and its first usable ability, the par build's if owned), its spec unlocks for those towers, and its difficulty; slot 2 is always the map's companion (`companionSlot` from `sim/companion.ts`, the harness's resolver too); modifiers from purchases are the `saveModifiers` seam (T204b), and `scriptFlags` are the save's set script-readable flags (`scriptFlagsOf`, T206b). Anything the sim still refuses (`FEATURE_GATES`) is left out, so a save that runs ahead of the sim plays instead of throwing. Without a save (`?map=`, `?skipIntro=1`) a battle uses the map's par loadout and Technician ability. It names `DEFAULT_MAP_ID` (`a1_m01`), the map a battle opens when nothing names one. It searches the live registries first, then the dev battle `render/__fixtures__/devBattle.ts` (`DEV_MAP_ID`, `?map=dev_range`: a 12×8 map with `dev_`-prefixed towers drawn with the real sprites and no Thumper lock, and Sgt. Bricks at a post with the real Suppressing Fire in slot 2), which the dev-layout smoke flows use. `BattleScene` gets everything through a `BattleSceneDeps` object (the sim, the host's bus, `frame`, `issue`, the interaction state), so it never imports `app/`.
- **Views:** pooled `EnemyView`, `TowerView`, `ProjectileView`, and `AllyView` objects in a `ViewPool` keyed by sim `uid` (`render/views/ViewPool.ts`: hidden and reused, never destroyed), created and released in response to sim events and positioned each frame from sim state. Each sync pass also stamps the views of live entities and sweeps the rest, so a missed event can't leak a view; a live entity with no view gets one lazily. Tower views draw the tier's base frame (a specialized tower's `spec_a`/`spec_b`), the head on the base's mount (aiming heads turn to their target's facing, using the `_t2` head from tier 2 and the spec's `_spec_<a|b>` head at tier 4 where the sprite authors them, `views/spriteInfo.ts` `baseFrame`/`headSuffix`; idle heads such as the Sprinkler's play their anim), and the `@glow` halos additively in `vfx`; selection swaps to the baked `+selected` variant. A tower holding fire (`tower.holdFire`, read in its `sync`) multiplies base and head by `steel.3` and shows the pause plate (`views/holdMarker.ts`) in `overlay` just above its art's first opaque row ([art-direction.md § Status visuals](../art/art-direction.md#status-visuals)). A tower on high ground stands on the block's top face, `ELEV_H` (8 px) up, and still sorts by its tile; its placement ghost is lifted the same, and the hover, selection, and teach highlights of a raised tile sit on the top face, sorted in `world` just in front of the block (a `decal` would be hidden under it). A locked or unaffordable tower doesn't arm (a HUD notice says why). After a build the slot **stays armed while another of that tower is affordable** (so several can be placed in a row, as in Kingdom Rush or BTD) and disarms otherwise (`app/hud.ts`). Selection, arming, and **aiming an ability** are exclusive: each drops the other two. Until the first build, every free pad blinks a `teal.3` highlight at 1 Hz (onboarding; steady under reduced motion). `hoverLook` returns one reused scratch object, so the per-frame hover allocates nothing. Nothing is hover-only, so touch can be added later. Keyboard input goes through `app/keys.ts` (below). A click and the keyboard cursor's Enter share the tile facts (`input/tileFacts.ts`) and the applying of the intent (`input/apply.ts`), so they always agree. **The tile cursor (T126):** keyboard-only play. Its tile lives in `BattleInteraction` (`cursor`, −1 while hidden; `cursorLast`, where it reappears; `cursorNav`, the line its arrows travel), independent of selection, arming, and aiming. The first arrow shows it on the selected tower, else its last tile, else the target nearest the map's middle (`cursorStart`); each later arrow moves it by **the cursor rule** (`input/cursor.ts` `cursorStep`): measure on the screen with vertical pixels counted double (an iso tile step is then the same length whichever way it goes); a target counts as "that way" within 45° of the arrow (so an edge-sharing iso neighbour counts for both arrows it sits between), and anything on that side counts only when nothing is in the cone; the score is the distance along the arrow plus half the distance off the line the cursor started on (kept while the same axis repeats), so repeated presses follow a straight screen line, zig-zagging over its tiles instead of drifting; ties go to the move along a grid axis (Up/Down change the row, Left/Right the column), then to the lower tile index; with nothing that way it stays. Its targets are the buildable tiles (pads, high ground, power nodes, and so every tower), or every tile while a strike is aimed (it lands on paths), or only the ground-route tiles while a path ability is aimed (an arrow from a tile it can't land on jumps to the nearest one); every pad of every map is reachable (tested). Enter (`commands.ts` `pressCursor`) resolves a left click on the cursor's tile. While the cursor shows, the hover feedback (highlight, ghost and ring, reticle) follows it instead of the pointer, and `views/CursorView.ts` draws `gold.3` corner brackets on its tile in the `overlay` layer ([art-direction.md §7](../art/art-direction.md#range-rings-and-placement)). A real pointer move or a click hides it; Esc with nothing selected, armed, or aimed hides it too. The HUD announces what it's on (below).

### UI: DOM overlay

**Decision: menus, the HUD, and dialogue are a Preact DOM overlay above the canvas. In-world UI (range rings, health bars, tells, floating numbers, placement ghosts) is drawn in Phaser.**

Why DOM:
- Stardust is **text-heavy** (dialogue, codex, memos, shop). DOM gives us text layout, wrapping, scrolling, and selection for free. Phaser text would need a hand-built layout engine.
- **Accessibility:** focus order, keyboard navigation, screen-reader labels, and user font scaling.
- **Forms:** player name and pronoun entry, and the save export/import text field.
- **Agent-friendly and testable:** Playwright can query DOM elements by role and text, and components are plain TSX.
- **Touch-ready:** native hit testing and scrolling.

How:
- `#ui` is a 640×360 box (in game pixels) layered over the canvas and scaled with CSS **`zoom: var(--ui-scale)`**, the same zoom as the canvas. All UI is authored in game pixels. (Use `zoom`, not `transform: scale`, so text re-rasterizes crisply and pointer coordinates stay correct.) `--ui-scale` is the canvas's CSS zoom, `n / devicePixelRatio` (`cssZoom` in `render/scale.ts`), not the integer `n` itself: one game pixel then covers exactly `n` *device* pixels, so text and icons stay on the device-pixel grid at fractional DPRs (1.25, 1.5) too. `app/boot.ts` sets it on `#ui` on boot and resize.
- The root has `pointer-events: none`; panels set `pointer-events: auto`, so clicks on empty space reach the canvas.
- **Screens:** `ui/Overlay.tsx` picks the screen from the `screen` signal: `screens/Title.tsx`, `screens/Campaign.tsx` (the Shift board), `screens/Base.tsx`, `screens/Settings.tsx`, the HUD (`hud/`) during a battle, or `screens/Results.tsx`. The screens' view models are `ui/screens/state.ts` (`runResult`, the last finished run; `slots` and `campaign`, written by `app/save.ts`); their styles are `ui/screens/screens.css`. Full-screen menus set `pointer-events: auto` (Results is a scrim over the frozen battle, so the canvas gets no clicks), and the game hotkeys are live only on the battle screen. ### Audio (`src/audio/`, M2+)

Procedural chiptune SFX and layered music on WebAudio (D001 #9, T205). Every sound and every piece of music is **data**; the synth plays any of it the same way. It never blocks the sim and never touches the sim's RNG.

- **Data.** A sound effect is a recipe (`audio/sfx/*.ts`, registry `sfx/index.ts`): up to 4 tone layers (square, triangle, sawtooth, sine, 25% and 12.5% pulse, or filtered noise), each with an ADSR envelope, an optional glide, arpeggio steps, vibrato, and a filter; plus the recipe's gain, priority (0–3), rate limit (`minGapMs`), voice cap (`maxVoices`), cosmetic pitch `jitter`, and an optional music `duck` level. Music is songs (`audio/music/`): tracks of pattern strings (`C4 - . E4`, drum letters `k s h o`, bars split by `|`) on instruments (`music/instruments.ts`), each track on a layer: `base`, `drums`, or `lead`. Looping themes are `title` and `act1_battle`; one-shot cues are `bright_sting`, `win`, and `lose`. `audio/recipes.ts` and `music/pattern.ts` validate it all, and the unit tests run them on every recipe, instrument, and song.
- **Which sound plays** is the pure `audio/eventSounds.ts`: tables keyed by attack kind (`ATTACK_SOUNDS`: hitscan → `rivet_shot`, lobbed → `thumper_launch` then `thumper_impact` when that shell's `ProjectileHit` arrives, pulse → `sprinkler_pulse`; a Cluster Thumper's bomblets, a lobbed shot with no target, are `BOMBLET_SOUNDS`: no launch, and one `bomblet_pop` whose 120 ms gap and single voice merge a scatter into a pop or two), by enemy (`ENEMY_POP_PITCH`), by ability (`ABILITY_SOUNDS`: the strike's charge on cast, its beam and boom when the zone lands, in sync with D022's FX; Suppressing Fire's `suppress_burst` rattle on cast), and by ally kind (`ALLY_SOUNDS`: Bricks's `bricks_ready` as he takes his post, and a chunky `bricks_shot` per `AllyAttacked`, rate-limited), and for fire control (`FIRE_CONTROL_SOUNDS`: `HoldFireChanged` clicks `hold_fire_on` stepping down or `hold_fire_off` stepping up; `SpareRunnersChanged` plays the same clicks 5 semitones higher). M2's moments have their own sounds (D059): `LinkFormed` rings `link_chime` (two bright notes a fourth apart), `TowerSpecialized` plays `specialize` (a thunk, then a rising sweep with a shimmer), and a `MedalProgress` forfeit plays `medal_forfeit` (a soft, kind falling third, never a buzzer). `suppress_burst` is 10 dB louder than T207b's and `sack_pop` 4 dB. Builds, upgrades (pitched up a step per tier), sells, unlocks, deaths, leaks, wave starts (an early call plays `wave_call` first), and the end of a map map to sounds or cues. The wave-clear cue comes from `WAVE_CLEAR_CUE` by act (none in Act III) and is held to the end of the frame, so the last wave's clear gives way to the win jingle.
- **The music director** (`audio/director.ts`, pure) picks the theme and layer levels: the title theme on the title, nothing on Results (its cue plays alone), and in a battle the act's theme (`BATTLE_THEME`) with the base always, drums while enemies are on the field or spawning, and the lead for the final two waves or at integrity 5 or less. Paused, the music plays at half level; a finished map fades it out. It also decides the countdown ticks (each of the last 3 s, the last a fifth higher) and the low-integrity klaxon (once as integrity crosses 5).
- **The synth** (`audio/synth.ts`) builds the voices and the bus graph: sfx → `sfx`; theme notes → per-layer gains → a theme fade (crossfades of 0.5 s; layers fade over 0.35 s) → `duck` → `music`; cues → `cues` → `music` (not ducked) → `master` → a glue compressor → a limiter (−4 dB, 20:1) → a soft clipper → out. Fixed trims sit under the player's volumes (`SFX_TRIM` 0.7, `MUSIC_TRIM` 0.32). The pure **voice book** (`audio/voices.ts`) admits each sound effect: its rate limit, its voice cap (the oldest makes way), and a global cap of 16 instances that steals the oldest voice of the lowest priority no higher than the new one, so a Rivet stream is a rattle and pops never drown an alarm. Music is scheduled 150 ms ahead of the audio clock by a 25 ms timer; late notes are dropped, not burst. The music ducks to the lowest active level: 0.55 while a radio line shows, and each big sound's `duck` while it rings.
- **The engine** (`audio/engine.ts`) creates the `AudioContext` lazily on the first user gesture (pointer or key), remembers the music until then, suspends while the tab is hidden, and is a silent no-op without WebAudio.
- **The binding** is `app/audio.ts`: `installAudio` at boot (the gesture unlock, the UI click and hover sounds on enabled buttons, the rejection buzz on every HUD notice, a radio blip per speaker on each radio line, the screen's music, and the settings' volumes) and `bindBattleAudio(host)` per battle (drained events through `eventSounds`, then after each frame the zone landings, countdown ticks, the integrity alarm, and the director's music). `?test=1` keeps audio off (no `AudioContext`); `&audio=1` turns it on.
- **Settings and keys.** `app/settings.ts` holds the volumes (master 0.8, music 0.7, sfx 0.8) and mute, saved under `stardust:settings` ([meta-runtime.md § Save system](meta-runtime.md#save-system)) behind a try/catch, so blocked storage just keeps the defaults. **M** mutes on every screen (`GLOBAL_BINDINGS` in `app/keys.ts`), as does the 16×16 speaker button at the HUD's top right and the title's corner (`ui/hud/MuteButton.tsx`, `aria-pressed` while muted). The volume sliders are on the Settings screen. The menus over the backdrop (Shift board, Base, Settings) keep the title's music.
- **Levels are checked, not heard.** `audio/offline.ts` renders every sound effect, cue, and theme, and a 10 s storm well past A1M1's W7 at 2× (every layer up, no ducking, 20 shot attempts and 10 pops a second, Thumper fire, leaks, a strike), through the real graph in an `OfflineAudioContext`; `smoke/audio.spec.ts` asserts every render is audible, never clipped, and peaks under 0.9 (−0.9 dBFS), every lone sound effect peaks under 0.8 before the limiter, and the storm stays under full scale. A recipe's own overload check (`recipes.ts`, `MAX_RECIPE_PEAK` 1) sums only the layers that can sound together (`overlapPeak`), so a rattle's separate cracks don't add up.

**"Everglow Bright" variants.** The campaign's motif is one six-note phrase (and its couplet) in seven arrangements ([story/bible.md §8](../story/bible.md#8-recurring-motifs)). As built, the phrase is G–C–E, F–D–C ("Ev-er-glow, Ev-er-glow"), and the couplet answers E–F–G–A–G ("brighter every day") and D–E–D–C ("clearing the way"); both Act I themes carry the couplet as their lead (`music/act1.ts`). Each arrangement is a named cue in `audio/music/cues.ts`, chosen by the presentation dials or by a script cue, never hard-coded per map (only `bright_sting` exists so far):

| Cue id | Arrangement | Used |
|---|---|---|
| `bright_sting` | Upbeat corporate wave-clear sting (the six notes); the full couplet on the PA at shift change | Act I `WaveCleared` |
| `bright_minor` | The same sting with minor-key bridges, then fully in minor from A2M4 | Act II `WaveCleared` |
| `hollow_hum` | Hummed off-key, out of tune, half backwards; drops in near Hollow units while other music ducks | Acts II–III, Hollow proximity |
| `leaving_hum` | Hummed slowly by one small voice (Pebble), then a second (Thrum, if spared) | A3M1 scene |
| `door_hum` | Hummed by Bricks over the radio, with Pebble humming along; loops while the SEAL waits | A3M3 SEAL |
| `choir_hymn` | Sung by the choir as a hymn, swelling with the number of voices; "clearing the way!" shouted | Finale Phase 2 |
| `dawn_major` | Major-key reprise, many voices | Finale Phase 3, credits |

In Act III there is **no wave-clear sting** (the jingle stops playing). The Hum Choir tower's harmony line carries the same phrase whenever a Choir is built ([design/towers.md](../design/towers.md#skitterkin-towers)).

## 5. Build, test, and deploy

The npm scripts that make up the test loop (D002) are defined here. **What each one checks and how to use them is in [conventions.md § The test loop](conventions.md#the-test-loop).**

| Script | Runs |
|---|---|
| `dev` | `vite`: dev server with HMR |
| `build` | `vite build` to `dist/` |
| `preview` | `vite preview --port 4173 --strictPort`: serves `dist/` |
| `typecheck` | `tsc -p tsconfig.pure.json --noEmit && tsc -p tsconfig.app.json --noEmit && tsc -p tsconfig.node.json --noEmit` |
| `lint` | `oxlint --type-aware && prettier --check .` |
| `format` | `prettier --write .` |
| `format:check` | `prettier --check .` (the formatting half of `lint`) |
| `test` | `vitest run`: unit, sim, content, save, balance-harness, and architecture tests |
| `test:watch` | `vitest` |
| `sim` | `node --experimental-strip-types tools/sim.ts`: headless balance sims for every map (args: `--map <id>`, `--seeds <n>`, `--build <name>`, `--report`) |
| `smoke` | `playwright test --trace off`: browser smoke tests against `npm run preview` |
| `check:docs` | `node --experimental-strip-types tools/check-docs.ts`: link and docs-index checks |
| `check` | **The whole gate:** `typecheck && lint && test && build && sim && smoke && check:docs` |
| `check:fast` | `typecheck && lint && test` (inner dev loop only, never the gate) |

From T101, `sim` and `smoke` exist as passing stubs ("0 maps") so the gate runs end to end before any map does.

`package.json` sets `"type": "module"` and `"engines": { "node": ">=22.6" }`.

**Config files:**
- `tsconfig.base.json`: shared strict options.
- `tsconfig.pure.json`: the pure modules, no DOM lib.
- `tsconfig.app.json`: the browser modules, with the DOM lib and Preact JSX (`"jsx": "react-jsx"`, `"jsxImportSource": "preact"`).
- `tsconfig.node.json`: Node-side code with `"types": ["node"]`: `tools/`, `smoke/`, `vite.config.ts`, `playwright.config.ts`, and `src/shared/architecture.test.ts` (it reads files with `node:fs`).
- `tsconfig.json`: a solution-style root (`"files": []` plus references to the three projects) for editors and oxlint's type-aware mode. `typecheck` runs the three projects directly.
- `vite.config.ts` (with `base: './'` so the build works from any subpath, JSX through Vite's `oxc` option with `importSource: 'preact'`, and Vitest config inline), `playwright.config.ts`, `.oxlintrc.json`, `.prettierrc.json` (with `.prettierignore`: Markdown is hand-formatted and not run through Prettier), `.editorconfig`.
- **Playwright's browser:** `playwright.config.ts` launches `CHROME_PATH` when it's set (Claude Code cloud sessions, where the preinstalled Chromium doesn't match the pinned Playwright's revision, so never run `playwright install` there), and otherwise Playwright's own Chromium (CI installs it). It passes `--use-angle=swiftshader --enable-unsafe-swiftshader` so headless WebGL always uses SwiftShader. Smoke runs always pass `--trace off`.

**Imports use relative paths with explicit `.ts` extensions** (`allowImportingTsExtensions`), and there are no path aliases. That lets the pure modules run unchanged in Vite, Vitest, and plain Node (`tools/sim.ts`), with no loader or alias config to keep in sync.

**Bundle:** Phaser goes in its own vendor chunk. Budgets: initial JS ≤ 1 MB gzipped, boot (compile content and bake sprites) ≤ 300 ms on a mid-range laptop.

### Deploy to GitHub Pages (once a remote exists, D001 #10)

1. Add `.github/workflows/deploy.yml`, triggered on push of tags `m*` (and manual dispatch): `npm ci`, `npx playwright install --with-deps chromium`, `npm run check`, then `actions/upload-pages-artifact` with `dist/` and `actions/deploy-pages`.
2. Enable Pages with source "GitHub Actions". With `base: './'` the site works at `https://<user>.github.io/stardust/` without config changes.
3. Saves are per-origin localStorage, so moving the host later orphans saves unless players use export/import. Document that in the release notes when it happens.
